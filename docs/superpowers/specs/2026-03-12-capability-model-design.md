# Capability Model & Skill Composition

**Date:** 2026-03-12
**Status:** Draft
**Scope:** Rename agent "skills" to "capabilities," add tool-side capability declaration, capability-based tool resolution, and skill-to-skill invocation via `depends_on`

**Group:** A (Conceptual Clarity) — addresses Gaps 1, 2, and 5 from tool/skill system audit

---

## 1. Problem

The word "skill" is overloaded:
- In agent configs (`config/agents/*.md`), `skills: ["file_read", "shell_execute"]` means "which tools this agent can use" — a permission list.
- In the skill catalog (`config/skills/*/SKILL.md`), a skill is a full workflow with instructions, context injection, output validation, and script tools.

These are fundamentally different concepts sharing the same name. Additionally:
- Tool resolution is 1:1 by name (`definitions_for_skills()` matches skill name to tool name directly). No indirection layer exists.
- Skills cannot compose — a complex workflow cannot invoke other skills as sub-routines.

## 2. Concepts After This Change

| Term | Meaning | Declared in |
|---|---|---|
| **Capability** | Abstract permission describing what an agent or skill can do (e.g., `"file_read"`, `"web_access"`) | Agent configs (`capabilities:`), Skill configs (`requires_capabilities:`) |
| **Tool** | Concrete implementation that provides one or more capabilities | `ToolRegistry` (built-in + TOML + script) |
| **Skill** | SKILL.md workflow with instructions, tools, context, output validation | `config/skills/*/SKILL.md` |

## 3. Capability Taxonomy

10 action-level capabilities:

| Capability | Built-in tools that provide it |
|---|---|
| `file_read` | `file_read` |
| `file_write` | `file_write` |
| `shell_execute` | `shell_execute` |
| `web_access` | `web_search`, `web_fetch` |
| `memory_read` | `memory_search` |
| `workspace_read` | `workspace_read` |
| `workspace_write` | `workspace_write` |
| `messaging` | `send` |
| `persona_write` | `update_persona` |
| `orchestration` | `spawn_subagent`, `spawn_subagents_batch`, `check_subagent_status`, `wait_for_subagents` |

Custom tools (TOML-configured) declare their own capabilities:
```toml
[[tools]]
name = "my_linter"
provides_capabilities = ["file_read"]
```

The taxonomy is open — new capability names can be introduced by custom tools without code changes.

## 4. Tool-Side Capability Declaration

Each `RegisteredTool` gains a `provides_capabilities: Vec<String>` field.

**Built-in tools** declare capabilities at construction time in `builtins/mod.rs`.

**TOML-configured tools** declare via `provides_capabilities` field in config:
```toml
[[tools]]
name = "custom_search"
description = "Custom search engine"
provides_capabilities = ["web_access"]
parameters = { type = "object", properties = { query = { type = "string" } }, required = ["query"] }

[tools.backend]
type = "http"
url = "https://search.example.com/api?q={query}"
method = "GET"
```

**Validation:** A tool with empty `provides_capabilities` is allowed (opt-in model). Such tools are only accessible via explicit `tools.allow` on skills (legacy path) or direct registry lookup.

## 5. Capability-Based Tool Resolution

### Agent Tool Resolution

`resolve_agent_tools(agent, registry)` is rewritten:

```
fn resolve_agent_tools(agent, registry) -> Vec<ToolDefinition>:
    agent_caps = agent.capabilities
    denied_caps = agent.denied_capabilities
    result = []
    for tool in registry.all_tools():
        if tool.provides_capabilities intersects agent_caps:
            # Exclude if ANY of the tool's capabilities is denied
            if NOT (tool.provides_capabilities intersects denied_caps):
                result.push(tool.definition)
    return result
```

**Deny semantics:** A tool is excluded if ANY of its `provides_capabilities` appears in the agent's `denied_capabilities`. This prevents tools from "sneaking in" via a non-denied capability when another capability they provide is denied. If a tool provides `["file_read", "web_access"]` and the agent denies `"web_access"`, the tool is excluded entirely.

**No special-casing.** Memory search, workspace tools, and any future tools are resolved uniformly by capability intersection.

**Prerequisite — workspace tools must be registered:** Currently `workspace_read` and `workspace_write` are NOT in `ToolRegistry` — they exist only as definitions generated by `workspace_tool_definitions()` and are handled by `ContextualToolExecutor`. Before this spec can remove their special-casing, they must be registered in `ToolRegistry` with `provides_capabilities: ["workspace_read"]` / `["workspace_write"]` and a new `ToolBackend::Contextual` variant (execution still delegated to `ContextualToolExecutor` at runtime). This registration is part of the implementation plan.

### Skill Tool Resolution

When a skill is invoked:

```
fn resolve_skill_tools(skill, registry) -> Vec<ToolDefinition>:
    # 1. Resolve from requires_capabilities
    caps = skill.requires_capabilities
    result = []
    for tool in registry.all_tools():
        if tool.provides_capabilities intersects caps:
            result.push(tool.definition)

    # 2. Legacy fallback: if requires_capabilities is empty, use tools.allow
    if caps.is_empty() and skill.tools.allow is not empty:
        result = registry.get_by_names(skill.tools.allow)

    # 3. Apply deny list
    result.retain(|t| t.name not in skill.tools.deny)

    # 4. Add script tools
    result.extend(skill.scripts.to_tool_definitions())

    # 5. Add invoke_skill:* synthetic tools (from depends_on)
    for dep_id in skill.depends_on:
        result.push(synthetic_invoke_skill_tool(dep_id))

    return result
```

### Registry API Change

```rust
// Removed
fn definitions_for_skills(skill_names: &[String]) -> Vec<ToolDefinition>

// Added
fn tools_for_capabilities(capabilities: &[String]) -> Vec<ToolDefinition>
```

`tools_for_capabilities` iterates all registered tools, returns those whose `provides_capabilities` intersects with the requested capabilities.

|---|---|---|
| `file_read` | `file_read` | Same |
| `file_write` | `file_write` | Same |
| `shell_execute` | `shell_execute` | Same |
| `web_search` | **`web_access`** | Groups web_search + web_fetch |
| `web_fetch` | **`web_access`** | Groups web_search + web_fetch |
| `memory_search` | **`memory_read`** | Renamed for consistency |
| `workspace_read` | `workspace_read` | Same |

| `send` | **`messaging`** | Abstracted |
| `update_persona` | **`persona_write`** | Abstracted |

### Skill Config (`config/skills/*/SKILL.md`)

```yaml
# Before
tools:
  allow: ["file_read", "web_fetch"]
  deny: ["shell_execute"]

# After
requires_capabilities: ["file_read", "web_access"]
tools:
  deny: ["web_search"]    # fine-grained exclusion of specific tools within a capability
```

`tools.allow` is deprecated. If present and `requires_capabilities` is absent, falls back to direct tool name matching (legacy). If both present, `requires_capabilities` takes precedence.

**Legacy compat bridge:** `SkillFrontmatter::apply_legacy_compat()` must be updated: if `requires_capabilities` is empty and `tools.allow` is non-empty, preserve `tools.allow` as-is. The resolution algorithm (Section 5) checks for empty `requires_capabilities` and falls back to `tools.allow`. No automatic conversion from `tools.allow` names to capability names — the legacy path uses direct tool name lookup.

## 7. Skill Composition via Invocation

### Declaration

A skill declares dependencies on other skills:

```yaml
# config/skills/full-review/SKILL.md
name: "Full Review"
requires_capabilities: ["file_read"]
depends_on:
  - "code-review"
  - "security-audit"
```

### Runtime Behavior

1. At invocation time, each `depends_on` entry becomes a synthetic tool definition:
   - Name: `invoke_skill:<skill-id>` (e.g., `invoke_skill:code-review`)
   - Parameters: `{ query: string }` — the input to pass to the dependent skill
   - Description: pulled from the dependent skill's catalog entry

2. When the LLM calls `invoke_skill:code-review(query: "review auth.rs")`:
   - Load the dependent skill (Level 2 from catalog)
   - Resolve its `requires_capabilities` → tools from registry
   - Run a **nested agentic loop** with the dependent skill's instructions + tools
   - Return the agentic loop's final response as the tool call result

3. The parent skill continues with the result.

### Constraints

- **Max call stack depth: 2.** `max_depth` is the maximum call stack depth including the root skill. Default 2 means: root skill (depth 1) can invoke a child skill (depth 2). A child skill at depth 2 cannot invoke further skills. Setting `max_depth: 3` would allow root → child → grandchild. Configurable via `invoke.max_depth` (default 2, minimum 1).
- **Cycle detection:** Validated at catalog load time (`SkillCatalog::validate_dependencies()`). Also enforced at runtime via a call stack. Rejects with clear error.
- **Cost attribution:** Nested skill's token usage and cost count toward the parent invocation's budget (`max_cost`). No separate budget.
- **Tool isolation:** Each nested skill gets only its own capabilities, not the parent's. The nested skill's `tools.deny` applies independently.
- **Cancel propagation:** Parent's `CancellationToken` is cloned and passed to the nested agentic loop.
- **Timeout:** Nested skill execution time counts toward the parent's `max_tool_runtime`. No separate timeout.

### Synthetic Tool Implementation

The `invoke_skill:*` tools are not registered in `ToolRegistry`. They are created dynamically during skill invocation and handled by a new `SkillInvocationToolExecutor` that wraps the catalog + registry + router.

A new `SkillInvocationToolExecutor` instance is created per skill invocation (not shared). The call stack is passed down to nested invocations:

```rust
pub struct SkillInvocationToolExecutor {
    catalog: Arc<SkillCatalog>,
    tool_registry: Arc<ToolRegistry>,
    router: Arc<LlmRouter>,
    call_stack: Vec<String>,  // passed by value, grows with each nesting level
    max_depth: usize,
}
```

When handling an `invoke_skill:*` call, the executor creates a NEW `SkillInvocationToolExecutor` for the nested skill with `call_stack` extended by the current skill ID. This avoids interior mutability — each nesting level gets its own executor instance.

This executor is composed into the `SandboxManager` alongside the `ContextualToolExecutor` for the parent skill's agentic loop. Tool calls starting with `invoke_skill:` are routed to it; all others go to the regular executor.

### `depends_on` is Optional

Skills without `depends_on` (or with empty `depends_on`) behave exactly as today. No synthetic tools are added.

## 10. Security & Validation

### Capability ↔ Security Relationship

The agent's `capabilities` list serves dual purpose:
1. **Tool resolution** — determines which tools the agent receives
2. **Security enforcement** — populates `AgentConstraints.allowed_capabilities` for `CapabilityManager` checks

These are kept in sync. There is no scenario where an agent has a capability for tool resolution but not for security. The `denied_capabilities` list also serves dual purpose: excludes tools from resolution AND blocks execution via `SandboxPolicy`.

### Startup Validation

After all tools are registered and all agent configs are loaded:
1. For each agent, warn if any declared capability has no registered tool providing it (e.g., `capabilities: ["quantum_computing"]` with no matching tool).
2. For each skill with `depends_on`, validate that all referenced skill IDs exist in the catalog.
3. Run `validate_dependencies()` to detect cycles in the `depends_on` graph.

### Conditional Tools

Some tools are conditionally registered (e.g., `send` requires an active `ConnectorSendProvider`). An agent with `messaging` capability will get zero tools for that capability if no connectors are configured. This is acceptable — the agent simply cannot send messages. No special handling needed.
