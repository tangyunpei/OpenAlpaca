# OpenAlpaca GUI Manual

OpenAlpaca GUI (`openalpaca-gui`) is a Tauri 2 desktop app — a React 19 +
TypeScript + Tailwind 4 frontend in a webview, with a small Rust shell whose
only job is finding (or starting) the local daemon. Everything on screen comes
from the daemon over HTTP, one WebSocket and one SSE stream; the webview itself
never reads the database, the config files or `discovery.json`.

One rule shapes the whole app and is worth stating before the tour: **nothing is
invented.** Where the daemon has no answer the GUI renders the empty state plus
a muted note naming what is missing, rather than a plausible-looking row. Two
such notes remain; they are named in "Surfaces the daemon does not serve" below.

## Run from a checkout

From the repository root:

```bash
cd apps/openalpaca-gui
bun install
bun run tauri dev
```

`tauri dev` runs `bun run prepare:sidecar:dev` (which stages the daemon binary
as the Tauri sidecar) and then the Vite dev server on port 1420, per
`src-tauri/tauri.conf.json`.

`bun run dev` starts the frontend alone. It is useful for layout work, but the
Tauri bridge is absent there, so the connection commands fail and the directory
picker in Settings → Extensions silently falls back to its text field.

The four CI gates for this app:

```bash
bun run check          # tsc --noEmit on both tsconfigs
bun run test           # vitest
bun run format:check   # prettier
bun run build          # production frontend build
```

## macOS package install (no Cargo on the target machine)

Build the artifact on a macOS build machine:

```bash
./scripts/release/package-macos.sh
```

Install it on the target machine:

```bash
./scripts/release/install.sh --file ./dist/openalpaca-macos-<target>-v<version>.tar.gz
```

`install.sh` also accepts `--url <https://.../archive.tar.gz>` instead of
`--file`, plus `--prefix <dir>` (binary install prefix, default
`~/.local/openalpaca`), `--app-dir <dir>` (macOS app bundle directory, default
`~/Applications`), and `--yes` (non-interactive overwrite).

After installation:

- GUI app path: `~/Applications/openalpaca-gui.app`
- CLI symlink: `~/.local/bin/openalpaca`

## Where things live

Everything the daemon owns is under one root, `~/.openalpaca/` on every
platform (`OPENALPACA_HOME_STORE` overrides it; absolute paths only). The GUI
does not choose this layout — it asks the storage crate for it
(`crates/openalpaca_storage/src/store/mod.rs`):

```text
~/.openalpaca/
  state/      openalpaca.db, discovery.json, openalpacad.lock, .master_key,
              backups/, logs/
  config/     the runtime config a GUI- or CLI-managed daemon reads
  plugins/    plugin directories, plus .permissions.toml, .config/<name>.toml,
              .data/<name>/ and .trash/ — all invisible to the plugin scan
  artifacts/ uploads/ sessions/ …   content, home scope
```

When the GUI spawns the daemon it sets the child's working directory to that
root and `OPENALPACA_CONFIG_DIR` to `<root>/config`
(`src-tauri/src/lib.rs`, `spawn_daemon`). A project you point the GUI at keeps
its own store at `<project>/.openalpaca/`.

First boot of a rebuilt daemon moves the contents of the legacy directory
(`~/Library/Application Support/OpenAlpaca` on macOS) into this root once. The
move is idempotent and resumable but **not reversible** — back the old
directory up first, and quit any old daemon, which otherwise blocks the move.

## Connection lifecycle

The webview asks the Rust shell for a connection; two Tauri commands are the
whole bridge (`src-tauri/src/lib.rs`):

- `ensure_daemon_running` — the boot path. It reads `state/discovery.json` and
  probes liveness by opening a TCP connection to the advertised address
  (300 ms). A live daemon is used even if the file's 24 h expiry has lapsed,
  because liveness is the authoritative signal. If nothing answers, the daemon
  is spawned detached (`setsid` on Unix) and the command polls for up to about
  five seconds (25 × 200 ms) for a daemon that both advertises itself and
  accepts connections.
- `get_connection_info` — the reconnect path. It re-reads discovery and checks
  the expiry without spawning anything.

Both return `{ baseUrl, token, instanceId }`. `instanceId` is the identity
guard: if it changes, the daemon restarted, so every `task_id`, `stream_id` and
`request_id` the client holds is dead and the app re-bootstraps rather than
merely reopening its socket (`src/lib/connection.ts`).

**Live events.** One WebSocket carries the daemon's whole `ServerEvent`
firehose: `GET /v1/events?token=…` — browsers cannot set WebSocket headers, so
the token rides in the query string. The socket drives cache invalidation
rather than being a data source of its own. It is best-effort: the daemon drops
frames for a lagged client without telling it, so a reconnect publishes a "you
may have missed events" signal and the query cache refetches. Reconnect backs
off from 1 s to a 30 s ceiling with ±20 % jitter (`src/lib/events.ts`).

**Streaming a turn.** Sending is `POST /v1/chat`, which answers
`{ stream_id, lane_key }`; the reply arrives on
`GET /v1/chat/stream/{stream_id}?token=…` (SSE). The `done` frame carries the
full content, not the tail, and is the source of truth — accumulated deltas are
only a live preview (`src/lib/chat-stream.ts`).

**Auth.** HTTP requests carry the discovery bearer token in a header. The
WebSocket, the SSE stream and the artifact content routes take `?token=`
inline, because neither `WebSocket` nor `EventSource` nor an `<img>` can set
headers.

## The shell

One rail, always mounted, and one of four views beside it
(`src/App.tsx`, `src/components/shell/`).

The **nav rail** is 196px and never scrolls. It holds, top to bottom: the
window traffic lights, the brand, `Chat` / `Work` / `Library`, a "Running now"
list, and at the bottom the ⌘K button, a connection row and `Settings`. The
Work item carries a badge counting `GET /v1/tasks?status=active` — whose SQL is
`status IN ('queued','running','paused')`, so the badge and the list agree.
Library carries **no** count: there is no count on the rail's budget, and a `0`
beside Library would be a claim about your library the app cannot make.

The window has a 1200px minimum width, which is what the chat view needs with
both of its side columns open; both of those collapse, so narrower windows stay
usable.

**Resizable panes.** Four columns are draggable and their widths persist
per-machine in `localStorage` (`oa-pane-widths`): the chat aside (300–600,
default 396), the Work run list (260–480, default 340), the Library list
(260–480, default 326) and the chat conversation list (200–360, default 236).

**Density.** The compact toggle in the chat header (also ⌘⇧D) narrows the
message gap, widens the transcript column from 720 to 780, and tightens the run
cards. It affects nothing else.

**Keyboard** (`src/components/shell/useGlobalKeys.ts`,
`src/components/overlays/`):

| Key | Effect |
|---|---|
| ⌘K / Ctrl+K | toggle the command palette |
| Esc | ordered ladder: close the palette → close the artifact picker → leave the file panel for the Work pane → deny a pending tool confirmation |
| ↵ | approve a pending tool confirmation (only while blocked, in chat, palette closed) |
| ⌘N | new background job |
| ⌘⇧S | steer the active run |
| ⌘1 / ⌘2 / ⌘3 | Chat / Work / Library |
| ⌘⇧D | toggle compact density |
| ⌘, | Settings → Tools |

The palette draws that same catalogue. Two of its rows exist only when their
state does — `Steer …` needs a run in `GET /v1/tasks?status=active`, and
`Approve …` needs a pending confirmation, which only the chat view knows about —
and it appends a `Find <filename>` row per hit from `GET /v1/artifacts?q=` as
you type.

## Chat

The chat view is a conversation column, a transcript, a composer, and — when
something is open in it — an aside (`src/views/chat/`).

**Conversations.** A lane holds many conversations (sessions) with exactly one
active at a time; the sidebar is the surface that makes that visible. The live
one sits on top, archived ones below it by `updated_at`, each labelled with the
project it is bound to, with `New chat`, rename, archive, delete and a
`Load more`. Clicking a row resumes it. A row whose runs were cut short by a
daemon restart carries an `N interrupted` badge.

Two rules the sidebar displays rather than enforces:

- Changing the window's project starts a **new** conversation, and the daemon
  does that on the turn itself. The sidebar only drops its resume pointer so
  the next turn names no session; the new row arrives on a `session_changed`
  frame.
- A turn addressed at a named conversation runs in **that** conversation's
  project, whatever the window is pointed at. When the two differ, the selected
  row says which one wins.

**Transcript.** Mono speaker labels over plain paragraphs — no avatars, no
bubbles. Besides messages it carries the run-report card for a background
workflow that finished in this session, session-local rows for a steer or a
queued follow-up (neither is a chat turn, so neither is persisted), the tool
confirmation banner, and chips for the files a turn carried in and the files its
run produced. The run pill and the artifact chips are read off stored history,
so they survive a reload; the recap *card* is built from the live
`workflow_started` / `task_status` frames and does not.

**Composer.** Two mutually exclusive states. Normally: a growing textarea, the
model picker, and today's spend. While a tool confirmation is pending the
textarea is **not rendered at all** — `Approve`, `Deny` and `Always allow`
replace it, which is why ↵ can never mean both "send" and "approve".
`Always allow` sends `approval_scope: "entire_tool"`, which the daemon honours
for the rest of the session.

The composer can also be *aimed*: `Steer` on a run card points it at that run
(`POST /v1/tasks/{id}/steer`, which answers `accepted` and the inbox depth),
and `Queue follow-up` points it at the lane
(`POST /v1/lanes/{lane_key}/followups`). The pending queue renders above the
composer, oldest first — the order the daemon claims them in — each row
cancellable and labelled either `follow-up` (work the daemon will run) or
`steering leftover` (a steering message a workflow exited before reading, which
is shown to the lead on the lane's next turn and never auto-run).

**Model picker.** Built from `GET /v1/models`. A pick is carried on that turn's
`POST /v1/chat` as `model` and persisted nowhere, so it governs this
conversation only; changing the daemon-wide default is a separate action in
Settings → Models & keys. A disabled provider contributes no models, so it
simply has no row here.

**The aside** is one slot with two modes, never both: the Work pane (run cards
for every run that is not `done`) or the file panel (one artifact, with the
same Preview / Diff / History renderers the Library uses, at compact size).
`‹ Work` restores the pane, `›` collapses the aside, and with the aside closed
the header grows a "running now" pill as the way back in.

## Work

A resizable run list beside a run detail (`src/views/work/`). The list is one
`GET /v1/tasks` window of 60 rows, partitioned client-side: every run that is
not `done` first (so a cancelled or failed run stays in the main list), then a
`Completed today` divider and compact rows under it. Live `task_status` frames
invalidate the query, so the list follows the daemon without polling.

The detail column scrolls as one — it has no sticky header, unlike the
Library's. It carries the run title over a meta line (status, the run's short
id, duration, steps, agent count, cost, and when it started), then either the
action group or, for a finished run, a terminal banner, then three cards:

- **Timeline** — the subagent swimlanes from `GET /v1/tasks/{id}/timeline`, one
  span per lane opened at its spawn, so a lane still working is drawn with a
  start and no end. A lane blocked on a tool confirmation goes red with an
  amber pending hatch and turns green the moment you answer. A failed or
  cancelled span is drawn neutral with its state spelled out, because the
  design's lane vocabulary has no colour for "failed" and painting it green
  would be a lie.
- **Output** — this run's files from `GET /v1/artifacts?task_id=`, each of
  which opens. A run whose files can only be read out of its free-form outcome
  blob shows them without pretending they open.
- **Event log** — this run's own persisted log,
  `GET /v1/events/history?task_id=`, including the tool calls the live socket
  could never attribute to a run.

Every card distinguishes "nothing happened" from "the read failed" and says
which.

**Run controls.** Eight, none of them decorative: `Cancel`, `Pause`, `Resume`
and `Start now` (all `POST /v1/tasks/{id}/action`), `Re-run`
(`POST /v1/tasks/{id}/rerun` — a *new* id, with `source_task_id` recording what
it was copied from), `Steer` and `Queue follow-up` (which aim the composer, as
above), and `Jump to chat`. Which subset a run shows follows its state: a live
run gets the transitions, a finished one gets the terminal banner with `Re-run`.

Two of them can be *disabled*, which is different from missing:

- `Steer` is owner-scoped and only reaches a live workflow, so a run the daemon
  would refuse arrives with `steerable: false` and the button carries the
  reason as its tooltip.
- On an **interrupted** run — one the daemon was running when it went away —
  `Resume` is the replay resume: the daemon rebuilds the run's loop history
  from its session log and continues it under the same id. That is experimental
  and off by default, so the button appears on the terminal banner only when
  `GET /v1/status` reports `routing.resume_enabled`. Otherwise `Re-run` is the
  way to restart it. Interrupted is terminal but is **not** an error, and is
  styled as a warning rather than a failure.

## Library

Two columns (`src/views/library/`). The left is `GET /v1/artifacts`, paged,
with the daemon's own unpaged `total` in the header — the size of the library,
not of this page — a `Load more`, and seven kind chips (`All`, `Docs`, `Code`,
`Output`, `Data`, `Media`, `Plans`). The chips filter what is *shown* rather
than re-querying, because two of the labels cover more than one artifact kind
while `?kind=` takes exactly one, and because that keeps `total` meaning one
thing.

Pins are server state (`PUT /v1/artifacts/{id}/pin`). The client keeps a
`localStorage` mirror so the star flips instantly, and every server answer
overwrites it, so the mirror cannot drift into claiming a pin the daemon does
not have.

The right column has a pinned header — `☆ Pin`, `Export`, `Reveal` — over
three tabs:

- **Preview.** An image is loaded straight by the browser from
  `…/content?token=`. HTML and SVG are shown as **source** by choice:
  rendering agent-authored markup inside the webview is a security review, not
  a missing route. Binary bytes are not characters, so nothing is drawn and the
  row points at Export. Anything over 512 KiB is refused before the fetch. A
  row whose bytes were deleted under the daemon says so — a blank pane would
  claim "nothing here", which is a different statement.
- **Diff.** `GET …/diff` for the newest pair. The `+ / −` counters are counted
  from the patch rather than read off the response, so they cannot disagree with
  the lines under them. A refusal is stated in its own words: `NOT_DIFFABLE`
  for an image or binary, `DIFF_TOO_LARGE` past the daemon's 8 MiB-per-side cap,
  and a single-version artifact has no pair to ask about at all.
- **History.** `GET …/versions`, newest first, each row carrying the daemon's
  own stored `+n −m` for that write (absent on v1 and for non-text kinds). A
  version with no author is not "unknown" — it is a **hand edit**: the daemon
  hashes an artifact's head on every read and records bytes that do not match
  its row as a version nobody in OpenAlpaca wrote. The row says so.

`Reveal` is labelled as the design labels it, but the only route behind it
(`POST /v1/files/{id}/open`) opens the file with the host's default
application rather than revealing it in Finder; the toast says so.

## Settings

A 220px section nav over a 660px-max body — the eight sections of
`src/views/settings/sections.ts`. A nav count that has not loaded is omitted
rather than shown as `0`, because a zero is a claim.

### Connection

The liveness dot and instance id (`GET /v1/health`), the endpoint, and
`Reconnect` (re-bootstrap, then reopen the socket).

Today's spend, runs and tokens come from `GET /v1/usage/summary`, including the
day itself — the daemon's UTC date rather than the browser's local one, so the
figure and the run filter mean the same day. There is **no daily budget and
none is coming**, so today's total has no denominator and no progress bar; the
panel instead names the two caps the daemon does enforce, per workflow and per
agent turn, with the daemon's own numbers.

`GET /v1/status` supplies uptime, the open database's `schema_version`, the
store's two size totals kept deliberately apart (uploaded bytes, which the
upload quota is read against, and produced bytes, which are never charged), what
the boot session-log sweep did, and `Copy log path`. The log path is `null` for
a daemon this run did not launch — a sidecar, a `cargo run`, or one that merely
found an older CLI daemon's leftover log — and the button is inert there,
because a path to a file this daemon did not write is worse than no path.

**The project.** One absolute path, typed, kept on this machine. The daemon
reads it as `x-workspace-path` on `POST /v1/chat`; runs started from here record
that project and the files they produce land in `<project>/.openalpaca/`. With
no project chosen the GUI sends no header and everything goes to the home
store. There is no project list and no browse dialog, because the daemon has no
project concept to enumerate.

**If the project directory moved**, the panel offers a re-base. A project store
records the root it was seeded at, so a store standing at a path it does not
name is a project that moved; the offer names the old path and counts the four
things still addressed under it — artifacts, conversations, runs and workspace
memories — and `Re-base` moves all four in one transaction
(`PATCH /v1/workspaces`). Nothing re-bases on its own. A re-base does not wait
for runs: while a run under the old root is still in flight the daemon refuses
the call outright (`409 WORKSPACE_BUSY`) and changes nothing, so the panel says
how many are in flight and holds the button until they finish — retry once they
do.

### Models & keys

The provider list and its keys (`GET /v1/settings/llm`), the model catalogue
(`GET /v1/models`), and picking the **daemon-wide** default model
(`PUT /v1/orchestrator/config`). The per-provider figure is today's, off
`GET /v1/usage/summary`'s `by_provider`; a provider with no calls today says so
rather than borrowing a lifetime number.

The per-provider switch writes the bit to `llm.toml` and moves the router
live (`PUT /v1/settings/llm/providers/{provider}/enabled`): a disable unloads
the provider and takes its models out of the registry, an enable puts them
back. Disabling the provider that serves the default model is refused with a
`409` naming it. A `200` is not always a load — enabling a provider with no
usable key writes the bit and leaves the router with nothing — so the row
carries the daemon's warning beneath the switch.

### Connectors

The connector list with its enable/disable action
(`POST /v1/connectors/{id}/action`), each row showing the connector's own
display name, the messages the daemon attributed to it over the last seven UTC
days, and — only where it disambiguates an `error` — whether the manager holds
a spawned handle at all. An `unwired` tag is a genuine client-side join: a
plugin declaring a connector that never appears in `GET /v1/connectors`.

`Connect service` is the first of the two remaining gaps: connectors are
compiled into the daemon, and no route adds one.

### Tools

The tool catalog from `GET /v1/tools`: name, description, provenance, whether
the tool asks first, and how often it ran today.

**There is no per-tool switch anywhere, and no route that would accept one.**
Governance is two axes: ALLOW is per-agent (a template's capabilities), ENABLE
is one toggle per MCP server and per plugin. So a builtin row renders no
control at all — a greyed-out switch would imply a switch exists — and an
extension tool renders a read-only provenance chip ("via MCP `github` —
enabled") that leads to its Extensions row. Availability is derived from the
agent's capabilities intersected with its extension being enabled, never
asserted per tool.

Skill health keeps a subsection here, fed by `GET /v1/skills/health` and named
from `GET /v1/skills`. A health row for a skill the catalog no longer holds (a
deleted directory, a disabled plugin's withdrawn contribution) keeps showing the
id the log has rather than a placeholder name.

### Extensions

One list over both kinds — MCP servers and out-of-process plugins — each row
carrying a `kind` chip, because both are governed by the same one-bit ENABLE
axis and an owner asking "what is turned on?" should not have to know which
mechanism a thing arrived through. The page asks for
`?include_orphaned=true`, so a plugin whose directory disappeared is visible
here and can be removed; the API hides orphans by default so scripts and
`openalpaca ext list` see only real extensions.

The toggle binds to the row's `enabled` bit, never to its state word: a plugin
that is enabled but crashed, loading or missing config shows the switch **on**
with a failure tag, because anything else would misreport what you asked for.
Each row names where its bit lives (`config/mcp.toml → [servers.<name>]
enabled = false`, or `plugins/.permissions.toml`), what a load could not
publish, the authorization URL for a server that answered 401/403 with one, and
the last refusal. Tone separates "you can fix it" from "it is broken", driven by
the API's own `actionable` flag.

Primary controls are the toggle plus, where they apply: `Approve` / `Deny` on a
plugin awaiting consent, `Configure` on one missing keys (one input per missing
key, posted one at a time — setting the last one starts the plugin without a
second call), `Retry` on a crashed or unreachable one, and `Remove` on an orphan
row. `Reload`, `Update` and `Uninstall` live in the row's overflow menu instead,
because nothing is wrong and the last two change what is *installed* rather than
whether it is on; both open an inline strip that has to be confirmed.

`Add extension` installs either kind:

- **A plugin is a directory.** The form takes an absolute path, picked or
  typed, and `Check` runs the daemon's dry run so the manifest is on screen
  before anything is copied. Installing **grants nothing**: the row lands
  unapproved, and `Approve` is the single action that starts it.
- **An MCP server is a declaration.** Writing it into your own
  `config/mcp.toml` is the consent, so there is no approve step — `Connect now`
  is the ENABLE bit.

`Update` replaces an installed plugin's tree: the incumbent goes to
`plugins/.trash/`, the replacement is renamed into place, and the load path
runs. Consent survives an update whose declared capabilities are unchanged;
otherwise it is reset and the response names what the replacement additionally
asks for.

An uninstall **deletes nothing**: a plugin's directory is moved to
`plugins/.trash/<id>-<stamp>/`, its `plugins/.data/<id>/` is kept unless you
clear the box (and moved, not removed, when you do), and the response says
where everything went. An MCP server's `[servers.<name>]` block is removed from
`config/mcp.toml`, and the server has to be turned off first. Nothing in
`.trash/` is auto-purged today. Installing from a URL is declined — it is its
own security review.

Routes: `GET /v1/extensions`,
`POST /v1/extensions/{kind}/{id}/{enable|disable|reload|approve|deny}`,
`GET|POST /v1/extensions/plugin/{id}/config` (the read redacts secrets),
`POST /v1/extensions/plugin` and `/v1/extensions/mcp` (install),
`POST /v1/extensions/plugin/validate` (the dry run),
`PUT /v1/extensions/plugin/{id}` (update), and
`DELETE /v1/extensions/{kind}/{id}` — with `?uninstall=true` for the real
removal, the bare verb staying the orphan-row one it always was. The
`extension_state_changed`, `extension_capability_withheld` and
`extension_capability_withdrawn` events arrive on the WebSocket and refresh the
affected rows; the old `/v1/plugins*` routes and `plugin_*` events no longer
exist.

### Agents

The template list (`GET /v1/agent-templates`) with each template's
**completed**-run count and the window it was counted over
(`?window=7d|30d|all`, default `7d`, grouped out of `subagent_span`), plus,
separately, which instances are running right now (`GET /v1/agent-instances`).
A template with no completed run in the window says so in words, because
`0 runs` reads like a metric that failed to load.

The per-template on/off switch is the second remaining gap: a template has no
`enabled` field and nothing would enforce one where subagents are spawned.

### Conversations

A read-only inventory across **every** lane — `GET /v1/sessions` — with each
conversation's title, message count, source, last-message stamp, the workspace
it is bound to, and whether it is still the live one. The GUI's own lane is one
row among them.

The write verbs live on the chat view's conversation sidebar, where the
conversation being operated on is the one on screen. That is deliberate: a
delete button beside a Telegram thread in a settings inventory is a worse
affordance than one beside the transcript it removes.

### Event log

The daemon-wide tail, `GET /v1/events/history`, newest first. The five coloured
tags are a client-side categorisation of the daemon's `event_type` string, which
is left untouched in the message column, so nothing is invented and nothing is
hidden. The panel states that this persisted log is narrower than the live
socket, which carries more variants than the daemon stores and cannot be
replayed. A single run reads its own slice through `?task_id=` on the same
route, in the Work detail.

## Surfaces the daemon does not serve

Two, and both say so in the UI rather than rendering a dead control
(`src/lib/unavailable.ts` is the registry, and the only source for this list):

| Gap | Surface | Why | Proposed |
|---|---|---|---|
| GAP-17 | `Connect service` in Settings → Connectors | Connectors are compiled into the daemon; `POST /v1/connectors/{id}/config` only sets a token on one that already exists | `POST /v1/connectors { kind, credentials }` |
| GAP-20 | the per-template toggle in Settings → Agents | `TemplateResponse` has no `enabled` flag, and nothing enforces one where subagents are spawned | `PUT /v1/agent-templates/{id}/enabled` |

Some other absences are **decisions**, not gaps, and are stated as such where
they appear: HTML and SVG previews are shown as source until the webview
rendering review happens; there is no daily spend bar because there is no daily
budget; there is no per-tool switch because ENABLE is per extension; the
replay-resume button is hidden unless the daemon enables it.

## Troubleshooting

**Cannot connect.** The shell probes TCP liveness before trusting
`state/discovery.json`, so a stale file is not the usual cause. Check that a
daemon can start at all (`openalpaca daemon status`, or run `openalpacad` in a
terminal and read its output) and that `state/discovery.json` exists and is
readable. In `bun run dev` there is no Tauri bridge, so both connection
commands fail by design.

**Connection flaps.** Watch the instance id in Settings → Connection: a change
means the daemon restarted, and the app deliberately re-bootstraps and drops
every id it held. Repeated restarts are a daemon problem — read the log path
that panel copies, or `state/logs/daemon.log` for a CLI-managed daemon.

**A list looks stale.** The event socket is best-effort and the daemon drops
frames for a lagged client without telling it. Anything that arrived over the
socket can therefore be behind; `Reconnect` in Settings → Connection forces the
refetch path.

**No models, or a provider that will not load.** Settings → Models & keys
shows the daemon's own reason under the switch — a `200` that wrote the bit
without loading the provider says so. `config/llm.toml` is seeded on first
daemon start and holds no keys until you add them.

**Library previews do not render.** Owner note, verbatim: "the Library's inline
previews were verified in the browser preview, not in the Tauri shell; if images
do not render there, the CSP `img-src` in `src-tauri/tauri.conf.json` is the
first thing to check." It currently admits `data:`, `blob:` and the loopback
origins (`http://127.0.0.1:*`, `http://localhost:*`), which is what
`…/content?token=` needs.

**An extension is off and will not come on.** The row names where its
disposition bit lives and what the load could not publish. A plugin needs
consent (`Approve`) before it runs at all, and one that is enabled but failing
keeps its switch on with a failure tag — that is the bit you set, not the state
it reached.

**Connector failures.** The connector row distinguishes a connector that
started and exited from one that never started. Beyond that, the Event log and
the daemon log are where the detail is.
