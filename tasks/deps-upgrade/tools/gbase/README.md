**Status: written 2026-10-11 (plan-rev3 §5.1 item 6a); amended 2026-10-12 for rev 3.9 (§5.1 item 6b: the Tauri pair first, no hold; rmcp unpinned). It moves no version. Its real sequence was REHEARSED on 2026-10-12 in scratch (plan-rev3 rev 3.11 — the rehearsal found the suite's two git-checkout tests and P14's seven pins, and the driver now handles both); the run of record belongs to the day of the cut, at or after 2026-10-17T20:08Z (DU-23 (a)), before P03.** What has run on the amended driver (2026-10-12): `bash -n`; `py_compile` of the three Python files; `--self-test` (16 cases, on a toy workspace, with `cargo +1.93.0`), and five mutants of the tools, each failing exactly the case or cases it targets (*The other modes*); `--dry-run` with the final phase on its own commit, whose tree outside `tasks/deps-upgrade/` is `d7f21b65`'s (43 anchors, 3 patches, Bun 1.4.3); `--with-stepbacks` refused (exit 2); `--edits-only --steps 8` on `05541f1b` and on `d7f21b65`, each compared by `diff -r` with an independent control (identical — *The other modes*; run before the review's fixes, which changed no edit: the fixed driver's `--edits-only` trees equal the earlier ones byte for byte).

`gbase.sh` is the named gate **G-base** (plan-rev3 §5.2): from one canonical scratch root `T=$(realpath "$(mktemp -d)")` it exports the base commit (`git archive <base> | tar -x -C $T/src`) and runs, in order, the toolchain step, **the Tauri pair's Rust half (step 1b, P31a)** and the re-cut's steps 2–8 of 2026-10-10 — each step its anchored manifest edits, its source hunks, its cargo commands, a `cargo check --workspace --all-targets --exclude openalpaca_gui` into `$T/target` and a lock snapshot compared with the shipped one — then the full suite, the docs check, the four bun gates and G-GUI. **It exits non-zero at the first failed command**; nothing is recorded-and-continued (the defect of the September drivers the audits rejected). Every log is under `$T/logs/`; the last line prints the lock differences and the test totals.

## How to run on the cut day

Prerequisites: `rustup` with the wave's toolchain installed (`cargo +1.99.0 --version` answers; the driver installs nothing), Bun **1.4.3**, P42's (rev 3.9) — used **ahead of P42's commit**: the driver runs on the tip before P42 lands (the order is the driver, then P42, P03, P31a …), so the root `package.json` still says `bun@1.4.2` when it runs (the owner's local Bun is 1.4.3 since rev 3.7) — network access for `cargo update` and `bun install`, Python 3.9+, perl, git, tar. Point `TMPDIR` at a scratch volume with room for two target directories (the workspace minus the shell is ≈ 2.7 GiB cold, the suite's test binaries more; `modernization-plan.md` §1). Nothing runs inside the repository: the export under `$T/src` is what is edited, built and tested. Every cargo call is `nice -n 10 env CARGO_TERM_COLOR=never CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=<the caller's, else 8> CARGO_TARGET_DIR=$T/target cargo +<toolchain> …`, one at a time, output to a file.

```sh
cd <the repository>
G=tasks/deps-upgrade/tools/gbase
TMPDIR=/path/to/scratch bash $G/gbase.sh --self-test --toolchain 1.99.0        # the failure modes still caught
TMPDIR=/path/to/scratch bash $G/gbase.sh --base <branch point> --bun <bun 1.4.3> --dry-run   # pre-flight + the plan, exit 0
TMPDIR=/path/to/scratch bash $G/gbase.sh --base <branch point> --bun <bun 1.4.3> --dates     # the run (≈ 30-60 min cold)
```

`--base` is the commit the wave's first commit will sit on (plan-rev3 §5.1 item 6: "the exact branch point"); `--toolchain` defaults to 1.99.0 (DU-2); `--steps N` runs the steps up to N (`1`, `1b`, `2` … `8`) and stops before the final phase; `--strict` makes an unexpected lock difference a failure (below); `--with-stepbacks` is refused (exit 2 — *Exit status* says why); `--dates` looks the differing versions up on crates.io at the end; `--repo` names another repository to export from. Record the result — the exit code, the RESULT line, the lock differences with their dates, the counts and `$T/logs` — in `tasks/todo.md` Chunk 25 (item 7), as plan-rev3 §5.1 item 6a asks; it also answers Appendix B #46 (step 2's comparison). Run it again whenever the base moves.

**The pre-flight runs before any cargo** (so a moved base fails in the second second, not the twentieth minute): the toolchain and Bun answer, every shipped file is present, the export is made, every anchor matches **exactly once** — the 23 manifest lines always (20 of the re-cut's steps, 3 of step 1b), and the 20 JS anchors (19 `package.json` lines, the `vite.config.ts` import) when the run reaches the final phase, 43 in all — and each of the three patches passes `git apply --check` against the pristine export. It also compares the base's `Cargo.lock` with the measured head's and says whether they are byte-identical, the same `(name, version)` set with other bytes (on `d7f21b65`: P24 added one `tower` dependency edge), or different. A base that already carries one of the patched files changed in a patch's hunk fails here with the patch's name; the remedy is to re-split from a diff against that base (`split-recut-diff.py`), not to force the patch.

### The lock comparison, and what "expected" means

After each step the lock is copied to `$T/locks/step-N.lock` and compared with the shipped snapshot. **Equal → ok.** Different → every differing package is printed as `name: old -> new` (`+`/`-` for added/removed) for a human, and the whole text is appended to `$T/logs/lock-differences.txt`. One class is expected and labelled, and is never a failure:

- **`[DU-25(v4)]` at steps 6, 7 and 8** — exactly `rmcp: 3.5.0 -> 3.5.1` and `rmcp-macros: 3.5.0 -> 3.5.1` (the spec `rmcp:3.5.0->3.5.1,rmcp-macros:3.5.0->3.5.1`). The shipped snapshots of those steps were cut with `--precise 3.5.0`; rev 3.9 takes the newest 3.5.x, and the measured cut's own first resolution was exactly those two moves before it stepped back [M-oct10: `recut-06-rmcp-update.log`, `recut-06-rmcp-update-precise.log`]; rmcp 3.5.1's manifest differs from 3.5.0's in its version and its `rmcp-macros` requirement only [D: the registry's `rmcp-3.5.{0,1}/Cargo.toml`]. The label is by version, not by name: rmcp moving anywhere else (a 3.5.2) is unexpected, listed and dated.

There is no hold filter any more (rev 3.9): every snapshot from step 2 on is the un-held re-cut's, so steps 2–5 compare with no label at all. Everything else is **unexpected**. Under DU-23 (a) — the cut on or after 2026-10-17 — an unexpected difference is expected to be **a release dated after 2026-10-10** (plan-rev3 §5.1 item 6: "the regenerated lock equals that file, or every difference is a release dated after 2026-10-10 and is listed with its date and its crate"); `--dates` prints the crates.io date beside each, and the human records the list. **`--strict`** turns any unexpected difference into a failure — the mode for a reproducibility check, not for the cut-day run. Step 1b's comparison is the one whose reference was not cut by the re-cut (above); a difference there that is not a release after 2026-10-10 is a finding about the 1.93/1.99 resolution, for the author to read.

### Exit status

- **0** — every step and gate passed; lock differences, if any, were printed (and under `--strict` there were none).
- **1** — the first failure: a cargo command (its log's last 30 lines are shown), an anchor matching 0 or 2+ times, a patch that does not apply, a lock that `--locked` changed, a step's version assertion (step 1b's pair at 2.12.3 / 2.7.x / 2.8.2; step 6's `rmcp`/`rmcp-macros` not one equal 3.5.x), a broken Tauri pair, a lock comparison `lockdiff.py` could not make (its exit 2, or output whose first line is not its `moved: …` summary, whatever its exit — `--strict` or not), a failed test, the docs check's set, a bun gate, G-GUI, or an unexpected lock difference under `--strict`. The message names the step and the log.

## The other modes

- **`--dry-run`**: the pre-flight (export, anchors, patches, toolchain, Bun), then the plan — every edit, every patch's files, every command with its log name, every pair check, every comparison — and exit 0; the export is removed, the pre-flight logs stay under `$T/logs`.
- **`--edits-only`**: the export with the steps' edits and patches applied (and, with `--steps all`, the JS edits), no cargo. **The proof on 2026-10-12:** `--edits-only --steps 8` compared by `diff -r` with a second export of the same base, built by a control that shares no code with the driver — `recut-source-only.diff` applied by `git apply`, then step 1b's three manifest lines written by a Python `str.replace` (each asserted once) — identical trees on two bases: on `05541f1b`, the newest base on which the diff applies whole, the diff applied whole; on `d7f21b65`, every file of the diff but the root `Cargo.toml` applied by `git apply`, and the root `Cargo.toml` by `git merge-file` (ours `d7f21b65`'s, base `7295f91b`'s, theirs `7295f91b`'s with the diff's hunks) with its one conflict resolved — P24's two `tower` lines right under P25's `tower-http` move, both kept. And the driver's tree differs from the plain export in exactly the 28 files of the diff plus `src-tauri/Cargo.toml`. (On 2026-10-11 the same proof ran on `c30e41df` and `e182f2ab`, without step 1b.)
- **`--self-test`**: a toy workspace (two path-dependent crates, no registry, `--offline`) under `$T`, built once into `$T/target` with the given toolchain, proving (i) a failing cargo command stops the driver with a non-zero exit and nothing after it runs (a sentinel file after the command never appears), (ii) an anchor matching zero or two times stops it and leaves the file unchanged, (iii) the lock comparison prints `a: 0.1.0 -> 0.1.1` and goes on, and under `--strict` the same difference stops it, (iv) an exact expectation `a:0.1.0->0.1.1` labels that move and passes `--strict`, while `a:0.1.0->0.1.2` does not cover it, (v) `expect_lock` passes a matching version and stops the driver on another, (vi) the pair check passes tauri 2.12.3 against api 2.12.x and dialog 2.8.2 = 2.8.2, and stops the driver on api 2.13.0 or dialog 2.8.1, (vii) a lock comparison `lockdiff.py` could not make stops the driver, `--strict` or not: a non-lock file — bytes that are not UTF-8, and UTF-8 text with no `[[package]]` — refused by `lockdiff.py` (exit 2) (`vii-nonlock`), and a `lockdiff.py` that dies before its summary — a syntax error: exit 1, Python's error report, no summary line — refused by `compare_lock`'s summary-line check (`vii-nosummary`) — plus the controls (a passing check, an anchor matching once, equal locks); 16 cases. Logs: `$T/logs/selftest-*.log`. Run with the toolchain that is installed (`--toolchain 1.93.0` before P03 moves the pin). On 2026-10-11 the self-test caught one real defect in the driver before it shipped: the summary line's `moved:` count was read by a regex that also matched inside `removed:`, so every difference read as none — parsed field-wise since. On 2026-10-12 five mutants of the driver were each run against the self-test, and each failed the case it targets and no other: `lockdiff.py` ignoring exact specs fails `iv-exact`; the dialog half of the pair check removed fails `vi-broken`; `compare_lock`'s summary-line check removed fails `vii-nosummary`; `lockdiff.py` without its refusals of a non-lock file and its catch-all fails `vii-nonlock` (its non-UTF-8 half is then stopped by the summary-line check, its no-`[[package]]` half is not); both of those removed — the state the review found — fails `vii-nonlock` and `vii-nosummary`, the non-UTF-8 comparison reading as "the same (name, version) set". The other twelve cases (`iv-exact-other` and `v-mismatch` among them) are controls or were not mutation-tested; the catch-all for an unforeseen error is not reached by any case (a direct run of a copy whose `main` raises exits 2).

## Scope — what G-base is and is not

G-base re-runs **the measured re-cut** with the pair first: the manifests' final state as `recut-source-only.diff` has it, P31a's Rust-half manifest form, and the lock procedure of plan-rev3 §5.1 items 6 and 6b, compared with the measured snapshots; then the final phase on the P31a + P31–P33 JS set. Commits of the wave that are **not** in that measured state are authored by hand per §5.3 and are not part of this gate: P01/P01a/P01b/P02 (CI and repository), P05 (the format pins), P13, P14 (the fixtures), P17/P17a, P19's protocol-offer pin and its `docs/api` regeneration, P23/P28 (optional), P24 (the CORS test), **P27a (`opener 0.9` — `opener = "0.8"` is a context line of the diff)**, P31a's JS half as its own commit makes it (the incremental v1 `bun install` and G-bundle), P34–P42, and rev 3.9's source changes named above. The driver changes no dependency version that the re-cut or P31a does not.

## Known limits

- bash 3.2 (macOS) and GNU bash alike; `ps -o pid= -o ppid= -o command= -A` for the orphan sweep (macOS and Linux). Paths with spaces in `TMPDIR` or the repository are not supported.
- Step 1b's reference is derived from stage D, resolved under `rust-version = "1.93"` (above); steps 2–8 compare with snapshots the re-cut cut itself.
- `lockdates.py` needs the network and crates.io's API; without them it prints `(date unavailable)` and the run still exits 0.
- A patch is cut at `7295f91b`'s code: a base whose copy of one of the 24 patched files changed inside a patch's hunk fails the pre-flight; re-split against it.
