## How to run on the cut day

Prerequisites: `rustup` with the wave's toolchain installed (`cargo +1.99.0 --version` answers; the driver installs nothing), Bun **1.4.3**, P42's (rev 3.9) — used **ahead of P42's commit**: the driver runs on the tip before P42 lands (the order is the driver, then P42, P03, P31a …), so the root `package.json` still says `bun@1.4.2` when it runs (the owner's local Bun is 1.4.3 since rev 3.7) — network access for `cargo update`, `bun install` and the registry reads (crates.io's API and the npm registry, User-Agent `openalpaca-deps-check`), Python 3.9+, perl, git, tar. Point `TMPDIR` at a scratch volume with room for two target directories (the workspace minus the shell is ≈ 2.7 GiB cold, the suite's test binaries more; `modernization-plan.md` §1). Nothing runs inside the repository: the export under `$T/src` is what is edited, built and tested. Every cargo call is `nice -n 10 env CARGO_TERM_COLOR=never CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=<the caller's, else 8> CARGO_TARGET_DIR=$T/target CARGO_BUILD_BUILD_DIR=$T/target cargo +<toolchain> …` (`cargo_cmd`), one at a time, output to a file. **The build dir is pinned to the target dir** (MF-5, its driver half): with a `[build] build-dir` configured — in the export's `.cargo/config.toml` once M63 lands, or in the real `CARGO_HOME`'s config the driver uses — `CARGO_TARGET_DIR` alone moves only the final artifacts, and the intermediates would land outside `$T`, where removing the scratch root never reaches them (measured on 1.93.0 and 1.99.0; the self-test's case xiii). The variable is chosen over stripping `build-dir` from the export's config because it leaves the export exactly the base (so `--edits-only`'s `diff -r` proof stands) and covers a `CARGO_HOME` config too; G-GUI's `$T/target-gui` and the suite's own environment carry it the same way.


`--base` is the commit the wave's first commit will sit on (plan-rev3 §5.1 item 6: "the exact branch point"); `--not-before` the cut instant (*The cut instant*); `--apply-step-backs` takes the freshness gate's step-backs (*The freshness gate* — without it the first young version ends the run with its sequence in the log); `--waivers <file>` names recorded DU-23 (c) waivers (none is recorded today: the owner's D2 (a), a waiver for rustls 0.23.46, never triggers at this cut — 0.23.46, published 2026-10-14T09:54:15Z, is eligible, and step 2's refresh takes it as an ordinary release); `--min-passed` the suite's floor (*The final phase*); `--toolchain` defaults to 1.99.0 (DU-2; the owner's D3 (a): P03 takes Rust 1.99.0 at the cut, and a one-line P03b moves to 1.99.1 through P03's gates once 1.99.1 is seven days old by the later of its publication times, the GitHub release of 2026-10-16T04:47:44Z — from 2026-10-23T04:47:44Z, that instant plus seven days to the second — so G-base, which runs before P03, keeps 1.99.0); `--steps N` runs the steps up to N (`1`, `1b`, `2` … `8`) and stops before the final phase; `--strict` makes an unexpected lock difference a failure (below); `--with-stepbacks` is refused (exit 2 — *Exit status* says why); `--dates` looks the differing versions up on crates.io at the end; `--archive-to` copies the evidence archive; `--repo` names another repository to export from; `--tauri`, `--dialog`, `--js-api`, `--js-cli`, `--tauri-crate NAME=VER` and `--js-pin NAME=VER` set the pins (D1 (a)'s values by default; *The cut instant*). Run it again whenever the base moves.

**The pre-flight runs before any cargo** (so a moved base fails in the second second, not the twentieth minute): the toolchain and Bun answer, `--min-passed` is given when the final phase runs, every shipped file is present, the export is made, every anchor matches **exactly once** — the 23 manifest lines always (20 of the re-cut's steps, 3 of step 1b), and the 20 JS anchors (19 `package.json` lines, the `vite.config.ts` import) when the run reaches the final phase, 43 in all — and each of the three patches passes `git apply --check` against the pristine export. ### The cut instant

A run (not `--dry-run`, `--edits-only` or `--self-test`) **refuses to start before it** — exit 2, before a scratch root is made — and the freshness gate's max date is that instant minus 7 days.

### The freshness gate

DU-23's 7-day rule, enforced on the Rust side (plan review MF-2 items 1 and 4; on the JS side `bunfig.toml` binds `bun install` from the install's time, and the final phase dates every entry of the new `bun.lock` against the cut — *The final phase*, item 3): **at every step from 1b to 8 — every step that moves the lock, the counterpart of P31a, P04, P06–P19 and P25–P30 — `lockdates.py --gate` reads crates.io for every `(name, version)` the step added or moved against the lock it started from** (`locks/step-<previous>.lock`; step 1's `--locked` check moves nothing) and requires each to be published at or before the max date (the cut instant minus 7 days) or listed in `--waivers` as a recorded DU-23 (c) waiver (`name@version  reason`, a reason on every line). For a too-young version it names the version to step back to — the newest release of that name that is semver-compatible with the locked one (cargo's caret), older, not yanked, not a pre-release unless the locked one is, and eligible; or the parent lock's own version in that range when that is newer — and prints the `cargo update -p name@locked --precise <target>` sequence **dependents first** by the lock's dependency lists (a dependent's requirement may bind its dependency: every 2026-10-14 Tauri internal requires `tauri-utils ~2.10.2`, so tauri-utils goes last), each spelled `name@locked`. A failed registry lookup is no verdict, and ends the run. Where the gate runs: right after the targeted update and its `--precise` at step 1b, after the plain refresh at step 2 (P04's "step back only packages younger than 7 days"), after `update -p rmcp` at step 6, and after the step's `cargo check` — which is what resolves those steps' new requirements — at steps 3, 4, 5, 7 and 8, followed there by `cargo check --locked` again when a step-back changed the lock.

**Without `--apply-step-backs` a young version ends the run**, its sequence on stderr and in `logs/fresh-<step>-0.log`. **With it**, the driver runs exactly the first `--precise` the gate named — never a target of its own — and runs the gate again (the steps cascade: an older dependent can pull in other versions), until the gate passes; a `--precise` cargo refuses is a named blocker (exit 1: a recorded waiver, or a later cut), as is a young version with nothing eligible to step back to at the head of the sequence — the driver takes the sequence's first entry of either kind and never steps past that one to a later entry, which may be its dependency; one with nothing eligible further down is left to the cascade (a dependent's older release may not need it) and ends the run when it reaches the head — a step-back named twice, or more rounds than twice the first young count plus ten. Every step-back applied is one line of `logs/step-backs.txt` (the step, the command, the publication time that required it), and the registry facts the gate decided on are `logs/registry-cache.json`; both are in the evidence archive. **The Tauri set** (MF-1 item 2): after the gate at step 1b, and again after step 2's, the lock must hold each of tauri, tauri-build, tauri-codegen, tauri-macros, tauri-runtime, tauri-runtime-wry, tauri-utils, tauri-plugin, tauri-plugin-fs and tauri-plugin-dialog at exactly one version, equal to its expected one, and each must be published at or before the max date (`logs/step-1b-tauri-dates.log`, `logs/step-2-tauri-dates.log`) — the check by minor only that let the 2026-10-14 internals through is gone.

### The lock comparison, and what "expected" means

After each step the lock is copied to `$T/locks/step-N.lock` and compared with the shipped snapshot. **Equal → ok.** Different → every differing package is printed as `name: old -> new` (`+`/`-` for added/removed) for a human, and the whole text is appended to `$T/logs/lock-differences.txt`. One class is expected and labelled, and is never a failure:

- **`[DU-25(v4)]` at steps 6, 7 and 8** — exactly `rmcp: 3.5.0 -> 3.5.1` and `rmcp-macros: 3.5.0 -> 3.5.1` (the spec `rmcp:3.5.0->3.5.1,rmcp-macros:3.5.0->3.5.1`). There is no hold filter (rev 3.9): every snapshot from step 2 on is the un-held re-cut's, so steps 2–5 compare with no label at all. Everything else is **unexpected**, and **no difference is expected by its date any more**: whether a version may be taken is the freshness gate's question, decided before the comparison (MF-2 — "every release dated after 2026-10-10 is expected", the earlier reading, would have passed the 2026-10-14 Tauri internals). - **1** — the first failure: a cargo command (its log's last 30 lines are shown), an anchor matching 0 or 2+ times, a patch that does not apply, a lock that `--locked` changed, a step's version assertion (step 6's `rmcp`/`rmcp-macros` not one equal 3.5.x), **the freshness gate** (a version younger than 7 days at the cut without `--apply-step-backs`; with it, a step-back cargo refused, a young version with nothing eligible to step back to, step-backs that do not converge; a failed registry lookup — no verdict — in any case), **the Tauri set** (a crate not at exactly its expected version, or one published after the max date), a pin of the pre-flight's registry check published after the max date, a broken Tauri pair, a lock comparison `lockdiff.py` could not make (its exit 2, or output whose first line is not its `moved: …` summary, whatever its exit — `--strict` or not), **the suite's verdict** (a signal, a build failure, a failure outside the expected pins, failed binaries that are not exactly the pins', a non-zero exit where none is expected, the passed count below `--min-passed`), the docs check's set, the new `bun.lock`'s freshness (an entry published after the max date and not waived, or no verdict), a bun gate, a write under the real HOME's Bun or npm caches, G-GUI, or an unexpected lock difference under `--strict`. The message names the step and the log.
- **2** — a usage error or a missing prerequisite (no `--base`, `cargo +<toolchain>` not installed, no `--bun` or no `--min-passed` when the final phase runs, a bad `--steps`, a `--not-before` that is not an instant with its zone, a pin that is not a version, a `--tauri-crate` or `--js-pin` naming another package, a `--tauri` other than the reference lock's without all eight internals), **a run started before `--not-before`** (nothing made), and **`--with-stepbacks`, refused in every mode** (before anything runs). It was DU-23 (b)'s fixed list for a cut before 2026-10-17: after the step-2 refresh, step `toml`, `toml_edit`, `uuid`, `serde_json`, `tokio-util` and `signal-hook` back to releases at least 7 days old. The list was measured on 2026-10-10, never covered the Tauri pair or the JS set, and is not what is young at any cut — at 2026-10-17T20:08Z the review counts about 33 entries of HEAD's lock that would need a step-back (MF-2). The freshness gate replaces it: `--not-before` names the instant and `--apply-step-backs` takes what is young then, measured on the day. ## Known limits

- bash 3.2 (macOS) and GNU bash alike; `ps -o pid= -o ppid= -o command= -A` for the orphan sweep (macOS and Linux). Paths with spaces in `TMPDIR` or the repository are not supported.
- Step 1b's reference was derived on 2026-10-17 for D1 (a)'s instant from the branch point's lock, under 1.99 (above): a base whose lock holds another (name, version) set, or a later cut, needs it re-derived. Steps 2–8 compare with snapshots the re-cut cut itself.
- The JS side has no step-back: an entry of the new `bun.lock` published after the max date ends the run, and the install's age limit is the committed `bunfig.toml`'s, counted from the install (the window in *How to run*). The compatibility report's alternative under C5 — each install run with its minimum release age set to the cut, which Bun 1.4.3's `bun install --minimum-release-age=<seconds>` takes and the report's JS leg emulated with a scratch `bunfig.toml` — is not built: the check was asked for, and the report leaves to the owner how DU-23 reads for transitive JS packages.
- The gate's step-back target is the newest eligible caret-compatible release (or the parent's version); it does not read a release's `rust-version`, features or targets, so cargo may refuse one — the run then stops naming it, and the remedy is a recorded waiver, a later cut, or the commit's own measured `--precise`. The registry reads need the network: the gate and the pins check fail closed without it (no verdict, exit 1); the `--dates` annotation prints `(date unavailable)` and the run still exits 0.
- A patch is cut at `7295f91b`'s code: a base whose copy of one of the 24 patched files changed inside a patch's hunk fails the pre-flight; re-split against it.
