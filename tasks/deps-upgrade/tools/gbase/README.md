## How to run on the cut day

Prerequisites: `rustup` with the wave's toolchain installed (`cargo +1.99.0 --version` answers; the driver installs nothing), Bun **1.4.3**, P42's (rev 3.9) — used **ahead of P42's commit**: the driver runs on the tip before P42 lands (the order is the driver, then P42, P03, P31a …), so the root `package.json` still says `bun@1.4.2` when it runs (the owner's local Bun is 1.4.3 since rev 3.7) — network access for `cargo update`, `bun install` and the registry reads (crates.io's API and the npm registry, User-Agent `openalpaca-deps-check`), Python 3.9+, perl, git, tar. Point `TMPDIR` at a scratch volume with room for two target directories (the workspace minus the shell is ≈ 2.7 GiB cold, the suite's test binaries more; `modernization-plan.md` §1). Nothing runs inside the repository: the export under `$T/src` is what is edited, built and tested. Every cargo call is `nice -n 10 env CARGO_TERM_COLOR=never CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=<the caller's, else 8> CARGO_TARGET_DIR=$T/target CARGO_BUILD_BUILD_DIR=$T/target cargo +<toolchain> …` (`cargo_cmd`), one at a time, output to a file. **The build dir is pinned to the target dir** (MF-5, its driver half): with a `[build] build-dir` configured — in the export's `.cargo/config.toml` once M63 lands, or in the real `CARGO_HOME`'s config the driver uses — `CARGO_TARGET_DIR` alone moves only the final artifacts, and the intermediates would land outside `$T`, where removing the scratch root never reaches them (measured on 1.93.0 and 1.99.0; the self-test's case xiii). The variable is chosen over stripping `build-dir` from the export's config because it leaves the export exactly the base (so `--edits-only`'s `diff -r` proof stands) and covers a `CARGO_HOME` config too; G-GUI's `$T/target-gui` and the suite's own environment carry it the same way.

```sh
cd <the repository>
G=tasks/deps-upgrade/tools/gbase
CUT=<the cut instant the owner chose, e.g. 2026-10-17T20:08Z — pending D1>
TMPDIR=/path/to/scratch bash $G/gbase.sh --self-test --toolchain 1.99.0        # the failure modes still caught
TMPDIR=/path/to/scratch bash $G/gbase.sh --base <branch point> --bun <bun 1.4.3> --min-passed <floor> \
    --not-before "$CUT" --dry-run                                               # pre-flight + the plan, exit 0
TMPDIR=/path/to/scratch bash $G/gbase.sh --base <branch point> --bun <bun 1.4.3> --min-passed <floor> \
    --not-before "$CUT" --apply-step-backs --dates --archive-to tasks/deps-upgrade   # the run (≈ 30-60 min cold)
```

`--base` is the commit the wave's first commit will sit on (plan-rev3 §5.1 item 6: "the exact branch point"); `--not-before` the cut instant (*The cut instant*); `--apply-step-backs` takes the freshness gate's step-backs (*The freshness gate* — without it the first young version ends the run with its sequence in the log); `--waivers <file>` names recorded DU-23 (c) waivers (none is recorded today); `--min-passed` the suite's floor (*The final phase*); `--toolchain` defaults to 1.99.0 (DU-2); `--steps N` runs the steps up to N (`1`, `1b`, `2` … `8`) and stops before the final phase; `--strict` makes an unexpected lock difference a failure (below); `--with-stepbacks` is refused (exit 2 — *Exit status* says why); `--dates` looks the differing versions up on crates.io at the end; `--archive-to` copies the evidence archive; `--repo` names another repository to export from; `--tauri`, `--dialog`, `--js-api`, `--js-cli`, `--tauri-crate NAME=VER` and `--js-pin NAME=VER` set the pins (today's values by default; *The cut instant*). Record the result — the exit code, the RESULT line, the step-backs (`logs/step-backs.txt`), the lock differences with their dates, the counts and the evidence archive — in `tasks/todo.md` Chunk 25 (item 7), as plan-rev3 §5.1 item 6a asks; it also answers Appendix B #46 (step 2's comparison). Run it again whenever the base moves.

**The pre-flight runs before any cargo** (so a moved base fails in the second second, not the twentieth minute): the toolchain and Bun answer, `--min-passed` is given when the final phase runs, every shipped file is present, the export is made, every anchor matches **exactly once** — the 23 manifest lines always (20 of the re-cut's steps, 3 of step 1b), and the 20 JS anchors (19 `package.json` lines, the `vite.config.ts` import) when the run reaches the final phase, 43 in all — and each of the three patches passes `git apply --check` against the pristine export. It also compares the base's `Cargo.lock` with the measured head's and says whether they are byte-identical, the same `(name, version)` set with other bytes (on `d7f21b65` and `3598a6fb`: P24 added one `tower` dependency edge), or different. A base that already carries one of the patched files changed in a patch's hunk fails here with the patch's name; the remedy is to re-split from a diff against that base (`split-recut-diff.py`), not to force the patch. **Last, a real run checks every pin it will take against its registry** (MF-2 item 4): the ten Tauri crates of step 1b's expected set on crates.io (`logs/preflight-pins-crates.log`) and, when the final phase runs, the three `@tauri-apps/*` pins with the cli's platform binaries and the sixteen P31–P33 pins on npm (`logs/preflight-pins-npm.log`) — each published at or before the max date, or a recorded waiver. `bunfig.toml`'s `minimumReleaseAge` measures 7 days from the install, not from the cut, which is why the driver checks the pins against the cut itself. `--dry-run` and `--edits-only` make no registry read.

### The cut instant

DU-23 (a)'s cut is **an instant with its zone** (plan review MF-1 item 3, G-03): a date alone admits releases early in one zone or the other, and the owner's clock is PDT (UTC−7). `--not-before <UTC>` takes `YYYY-MM-DDTHH:MM[:SS]Z` and nothing else (a date alone, a time without `Z`, an offset: exit 2, in every mode). A run (not `--dry-run`, `--edits-only` or `--self-test`) **refuses to start before it** — exit 2, before a scratch root is made — and the freshness gate's max date is that instant minus 7 days. The default is rev 3.9's **2026-10-17T20:08Z (13:08 PDT)**, standing until the owner answers **D1** (`tasks/pending-decisions.md` §4.3), whose recommendation is **2026-10-21T19:53Z (12:53 PDT)**, when the whole 2026-10-14 Tauri train is 7 days old. Pass the instant the owner chose; the driver takes no side, and each answer is a set of arguments:

- **A cut after the 2026-10-14 train is eligible (D1 (a))**: `--not-before` that instant, and the Tauri pair re-anchored on the family eligible then, measured on the day — `--tauri`, `--dialog` (the crate's `=` and its npm twin), `--js-api`, `--js-cli`, and either a re-derived step-1b reference lock (measured on the day, replacing `locks/guiD-lock-01b-pair.lock`, whose eight internals are the defaults) or `--tauri-crate NAME=VER` for each of the eight (a `--tauri` that is not the reference lock's tauri without all eight is refused, exit 2: the internals belong to their tauri). Nothing Tauri is then young; the gate still steps back whatever else is (P04's rule).
- **The cut kept at 2026-10-17T20:08Z (D1 (b))**: the defaults, with `--apply-step-backs`: the gate steps the 2026-10-14 internals back one `--precise` at a time, dependents first (tauri-utils last), measured on the day — MF-1 (b)'s procedure — and step 1b's exact check holds the result to the reference lock's internals.
- **"The Tauri set is never held" read as overriding the 7-day rule for Tauri's internals**: each young Tauri version listed as a recorded DU-23 (c) waiver in `--waivers`, and the expected set passed as in the first case.

The re-anchoring's version literals are written once the answer is in (a tooling commit re-deriving the reference lock and the defaults), never ahead of it. The pins' defaults are rev 3.9's: tauri 2.12.3 (`--precise`), tauri-plugin-dialog `=2.8.2` and `@tauri-apps/plugin-dialog` 2.8.2, `@tauri-apps/api` 2.12.3, `@tauri-apps/cli` 2.12.2, the eight internals as the reference lock holds them, and the P31–P33 JS pins of *The final phase*.

### The freshness gate

DU-23's 7-day rule, enforced on the Rust side (plan review MF-2 items 1 and 4; `bunfig.toml` already binds `bun install`): **at every step from 1b to 8 — every step that moves the lock, the counterpart of P31a, P04, P06–P19 and P25–P30 — `lockdates.py --gate` reads crates.io for every `(name, version)` the step added or moved against the lock it started from** (`locks/step-<previous>.lock`; step 1's `--locked` check moves nothing) and requires each to be published at or before the max date (the cut instant minus 7 days) or listed in `--waivers` as a recorded DU-23 (c) waiver (`name@version  reason`, a reason on every line). For a too-young version it names the version to step back to — the newest release of that name that is semver-compatible with the locked one (cargo's caret), older, not yanked, not a pre-release unless the locked one is, and eligible; or the parent lock's own version in that range when that is newer — and prints the `cargo update -p name@locked --precise <target>` sequence **dependents first** by the lock's dependency lists (a dependent's requirement may bind its dependency: every 2026-10-14 Tauri internal requires `tauri-utils ~2.10.2`, so tauri-utils goes last), each spelled `name@locked`. A failed registry lookup is no verdict, and ends the run. Where the gate runs: right after the targeted update and its `--precise` at step 1b, after the plain refresh at step 2 (P04's "step back only packages younger than 7 days"), after `update -p rmcp` at step 6, and after the step's `cargo check` — which is what resolves those steps' new requirements — at steps 3, 4, 5, 7 and 8, followed there by `cargo check --locked` again when a step-back changed the lock.

**Without `--apply-step-backs` a young version ends the run**, its sequence on stderr and in `logs/fresh-<step>-0.log`. **With it**, the driver runs exactly the first `--precise` the gate named — never a target of its own — and runs the gate again (the steps cascade: an older dependent can pull in other versions), until the gate passes; a `--precise` cargo refuses is a named blocker (exit 1: a recorded waiver, or a later cut), as is a young version with nothing eligible to step back to at the head of the sequence — the driver takes the sequence's first entry of either kind and never steps past that one to a later entry, which may be its dependency; one with nothing eligible further down is left to the cascade (a dependent's older release may not need it) and ends the run when it reaches the head — a step-back named twice, or more rounds than twice the first young count plus ten. Every step-back applied is one line of `logs/step-backs.txt` (the step, the command, the publication time that required it), and the registry facts the gate decided on are `logs/registry-cache.json`; both are in the evidence archive. **The Tauri set** (MF-1 item 2): after the gate at step 1b, and again after step 2's, the lock must hold each of tauri, tauri-build, tauri-codegen, tauri-macros, tauri-runtime, tauri-runtime-wry, tauri-utils, tauri-plugin, tauri-plugin-fs and tauri-plugin-dialog at exactly one version, equal to its expected one, and each must be published at or before the max date (`logs/step-1b-tauri-dates.log`, `logs/step-2-tauri-dates.log`) — the check by minor only that let the 2026-10-14 internals through is gone.

## Known limits

- bash 3.2 (macOS) and GNU bash alike; `ps -o pid= -o ppid= -o command= -A` for the orphan sweep (macOS and Linux). Paths with spaces in `TMPDIR` or the repository are not supported.
- Step 1b's reference is derived from stage D, resolved under `rust-version = "1.93"` (above); steps 2–8 compare with snapshots the re-cut cut itself.
- The gate's step-back target is the newest eligible caret-compatible release (or the parent's version); it does not read a release's `rust-version`, features or targets, so cargo may refuse one — the run then stops naming it, and the remedy is a recorded waiver, a later cut, or the commit's own measured `--precise`. The registry reads need the network: the gate and the pins check fail closed without it (no verdict, exit 1); the `--dates` annotation prints `(date unavailable)` and the run still exits 0.
- A patch is cut at `7295f91b`'s code: a base whose copy of one of the 24 patched files changed inside a patch's hunk fails the pre-flight; re-split against it.
