## The headline finding — the GUI half needs another launcher

Launched as plan-rev3 §5.2's launcher (iii) prescribes (`sandbox-exec -f scripts/eval/memory/loopback-only.sb <bundle>/Contents/MacOS/openalpaca_gui`), **the app's webview never reaches its daemon**: in every launch checked (8 of 18) `GET /v1/status`'s `busy.connected_clients` stayed 0 and the daemon's port had no peer. The unified log shows WebKit's Networking process "Setting sandbox state flag to block network access" in all 18 of these launches and in no other app's, and its loopback connects failing with `EPERM` (177 against 21 "Network is down" in one process) — WebKit's own network policy, triggered by the UI process running under the profile. The sidecar itself is confined as intended (`sandbox_check(network-outbound) = 1` for the shell and the daemon, the daemon a child of the shell), and the two-request proof passed. Consequences: the shell and WebKit memory/CPU rows below were measured with a **disconnected** webview and are not a GUI baseline for Q10; and **E5's step 4 uses the same launcher**, so its GUI checks would fail the same way. Recommendation (rev 3.8): for any GUI check, start the daemon first under launcher (i) on the isolated store, then launch the app **unsandboxed** with the same `OPENALPACA_HOME_STORE` and `OPENALPACA_CONFIG_DIR` — the shell reuses a live daemon rather than spawning one, so the only process with outbound reach beyond loopback stays confined; keep launcher (iii) for the cold daemon-ready figure only. *Corrected 2026-10-17 (review MF-4):* that holds **only until the first in-app Start**. Settings → Connection → `Start daemon` clears the stop intent and reconnects (`startDaemon`, `apps/openalpaca-gui/src/lib/daemon-control.ts:146-151`); with no live discovery file `ensure_daemon_running` spawns the bundled sidecar (`src-tauri/src/lib.rs:39-52`), and `spawn_daemon` execs it under `setsid` with only `OPENALPACA_CONFIG_DIR` and the managed-log variable set (`:343-366`) — no sandbox profile — so every check after an in-app Start (a model turn, the memory flows, a file write) runs on a daemon with full outbound network, and the shell-side two-request proof cannot see it, since it proves the shell's sandbox, not a process the shell spawned. Q00's own runs made no in-app Start (rows (2), (3) and (7) reused the live daemon), so its figures stand. A check that stops and starts the daemon from the app — G-bundle leg A, E5 step 5, M74's gate — needs the in-app Start confined, and confinement proven after it by this file's method (`sandbox_check(network-outbound)` on the new pid, a refused public request in its log, `ps` showing the running pid is the confined one); plan-rev3 rev 3.13 (§5.2's *Every in-app Start is confined*, G-bundle leg A, E5) and modernization-plan rev 2.2 (M74) carry that amendment (the review's MF-4).
