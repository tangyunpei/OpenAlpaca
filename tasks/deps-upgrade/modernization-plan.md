## 0. Summary

Where the groups wrote "owner decision" out of caution rather than because a rule-5 trigger applies, this document reclassifies the item as work and says so; where they disagree, it says which evidence wins and why. ### 1.1 What the owner's number can and cannot tell us

The owner's `cargo clean` removed **530,884 files, 147.6 GiB** — 147.6 × 2^30 / 530,884 ≈ 298.5 kB ≈ **292 KiB per path**. Both figures are per *path*: cargo 1.93.0's `CleanContext::rm_rf` adds 1 to `num_files_removed` and `meta.len()` to `total_bytes_removed` for every non-directory `walkdir` entry, and its own comment says it over-counts hard-linked files and under-counts block sizes [D: `rust-lang/cargo@083ac5135` `src/cargo/ops/cargo_clean.rs:455-521`, fetched to `SP/logs/fetch/rev2/cargo_clean-083ac5135.rs`] — so 530,884 is a count of names (a hard-linked object once per name, as the `paths` column below) and 147.6 GiB is an upper bound on the unique bytes. **What the levers mean:**
- **Incremental is the only lever with a large byte effect** (−42 % on one crate's test build; −53 % on the whole documented set). Where it lives decides who pays the edit cost: `[profile.test] incremental = false` affects every `cargo test` (the owner's included), `[profile.dev]` every build, `CARGO_INCREMENTAL=0` whoever has it in the environment.
- **`split-debuginfo` decides the path inflation, not the bytes.** macOS's default `"unpacked"` keeps every codegen-unit object and links it into `deps/` (512 for storage: 256 per target × lib and test). `"off"` removes them (−29 % paths, 0 % bytes) **but a test backtrace then shows function names without `at ./src/lib.rs:N:M` lines** — measured on the toy with `RUST_BACKTRACE=1`: baseline and `"packed"` print the two `at ./src/lib.rs:8:…` frames, `"off"` prints none. That is precisely the file:line information `Cargo.toml:155-157`'s comment keeps `debug = "line-tables-only"` for ("readable backtraces") [C]. `"packed"` keeps the frames, has no objects in `deps/`, and costs +6 % bytes (one `.dSYM` per binary) and a `dsymutil` per link.
- **`debug = 0`** saves 10 % and removes the objects, at the price of no line tables anywhere.
- **`codegen-units = 16`** removes 94 % of the objects (−53 % paths) for −1 % bytes. Its edit-rebuild cost on `openalpaca_storage` is below the driver's 1-second resolution [M: `cgu-storage.tsv`, `cgu-{baseline,cgu16}-{0,1,2}.log`]: cold 8 s against the baseline's 9 s in the same session, two successive real edits ≤ 1 s each under both settings (a sub-second difference is not excluded), paths 835 → 908 → 940 against 1,795 → 2,828 → 3,340, `.o` names in `deps/` 32 → 64 → 96 against 512 → 1,024 → 1,536, bytes within 1 %. Its effect on `openalpaca_core`'s or the daemon's rebuild, where 16 coarser units could mean more code per recompiled unit, is [NE].
- **`strip = "debuginfo"`** only shrinks the test binary by 2 MiB.

**Six successive real edits of `openalpaca_storage`** (a new private function appended each time), test build, four settings [M: `churn-storage.tsv`]:

rustc keeps the previous session (two `s-*` per hash dir, never more — the toy ran six edits with the same result), so **bytes stop growing after the first edit for a fixed hash; the paths do not**: every session links its mostly-reused objects into `deps/` under a new name, 512 more names per edit over the same 1,291 inodes. Over months this is the mechanism that turns a 10–20 GiB target into a 500,000-path one. Objects whose session was deleted and that no newer session reuses stay in `deps/` as orphans (17 of them, 3.6 MB, after the toy's six edits; none yet in storage's six) — a slow byte leak on top [M].

### 1.8 Stability facts: what stable cargo can and cannot do [M: `toy-builddir.log`, `clean-gc-dryrun.log`, `toy-feature-unification.log`]

- **`build.build-dir` is stable on 1.93.0 and on 1.99.0**: `cargo --config 'build.build-dir="<dir>"' check` on a toy crate prints **no warning of any kind**, exit 0; `target/` keeps only `CACHEDIR.TAG` and the lock (4 KB) while `.rustc_info.json`, `debug/{.fingerprint,incremental,deps,build,examples}` land in the build-dir (26.6 MB on 1.93.0, 27.7 MB on 1.99.0, whose lock is named `.cargo-build-lock`). With `build`, the **final** artifacts (`toycrate`, `libtoycrate.rlib`, their `.d`) land in `target/debug/`; with `test --no-run` the **test executables land in `<build-dir>/debug/deps/`**. So a build-dir moves essentially all of the growth; `target/` keeps the uplifted binaries and rlibs (≈ 0.45 GiB in A). Stabilised in Cargo 1.91 (2025-10-30); templating `{workspace-root}`, `{cargo-cache-home}`, `{workspace-path-hash}` available [Docs: Cargo Book CHANGELOG, config → `build.build-dir`; `SP/logs/fetch/cargo-config.txt:432-443`]. Cargo 1.100 (2026-11-12) changes the build-dir's internal **layout** ("not a stable interface"); `-Z build-dir-new-layout` is refused on stable 1.99.0 [M]. `prepare-sidecar.ts:42-43` reads `target/<profile>/openalpacad` [C] and keeps working under a build-dir because final artifacts stay in `target/`; nothing in `scripts/` or `apps/openalpaca-gui/scripts/` reads `deps/` by hand [C: grep]. **What build-dir does not do:** it deletes nothing, shares nothing between invocations with different features, and does not stop the growth — it relocates it. One sharing effect is real: a fixed build-dir (no `{workspace-path-hash}`) used by several checkouts or worktrees of the same repository lets them reuse each other's artifacts (cargo's build lock serialises them); whether agent sessions build in separate worktrees is [NE].
- **`cargo clean gc` is refused on stable**: `cargo +1.93.0 clean gc --dry-run` and `cargo +1.99.0 clean gc --dry-run` both exit 101 ("the `cargo clean gc` command is unstable, and only available on the nightly channel of Cargo", tracking issue #12633); `-Z gc` is listed by `-Z help` on 1.93.0, 1.98.1 and 1.99.0 and refused on all three. It concerns the **global cache in `$CARGO_HOME`** (registry sources, `.crate` files, index, git checkouts), never `target/` [Docs: Cargo Book unstable → gc; `SP/logs/fetch/cargo-unstable.txt:1175-1212`]. `cargo clean --dry-run` works ("Summary N files, X total"); `-p <crate>`, `--profile`, `--release`, `--doc` are the only selective forms and none is age-based. **There is no cargo-native age- or size-based cleaning of `target/` on any installed toolchain.** The owner's global cache, `~/.cargo/registry`, is 2.1 GiB [M: `du`] — not where the problem is.
- **`-Z feature-unification` is refused on stable**: `--config 'resolver.feature-unification="workspace"'` on 1.93.0 and 1.99.0 prints `warning: ignoring resolver.feature-unification without -Zfeature-unification` and proceeds in the default `selected` mode. The stable remedies for the duplication the A table shows are the invocation set itself (always select the same packages → the same unification) or `default-members` (DU-M1). How much steps 1, 2 and 3 duplicate: each adds a complete tower of the workspace crates (stems 1 → 2 → 3) and of the dependencies whose features differ (distinct stems 1,711 → 4,062 → 8,855).
- **Cargo 1.99 disables incremental compilation by default when `CI` is set** [Docs: RELEASES.md 1.99; the rust-modernization group's reading] — nothing here runs under `CI` locally.
