## 0. The directive, read as three requirements

Owner: *"redesign or improve our current chat compacting system to better integrate with the memory system for the chat compact and hints or the memory after the compact for the agent to better pick up from previous chat and continue the work."*

- **R1** What in-loop compaction learns must not die with the loop. Today the `LlmSummary` tier makes two model calls — an extraction whose items are counted and dropped (`prompt_ctx/compaction/graduated.rs:100`) and a summary that lives only in the loop's `Vec<ChatMessage>` (`context_budget/compaction.rs:180`); `LoopResult` carries no messages, the `compaction` log record carries counts only (map §1.4–§1.5).
- **R2** After a mid-turn compaction, after a break, and on a new conversation on the same lane and project, the model gets *where we left off* — open work, decisions, the next step — and knows where the fuller record is. Today nothing records open work (map Gaps 7–9).
- **R3** The three summarisers — the loop's, the background `session.summary` (12-row lag, trimmed first, off the wire, map §2.2) and the episode writer (map §4.4) — become one coherent, cheaper mechanism.

The panel's verdict (both judges): continuity belongs on the **session row and in the history layer**, not in memory notes — a memory-first design has to reverse the frozen summary shape (03 §7a: a `Summary` provenance carries no `fact_key`, no `supersedes`), route delivery through a lexical recall that cannot find "go on", and add a paid call to every short session. Memory keeps what it has: the episode note as the findable *record*, learned facts from rows.

## 1. Summary

1. **One artefact**: the conversation's **working state** — fixed-shape JSON on the session row (`topic, goal, done[], asked[], decisions[], open[], next, refs[]`; Claude Code's continuation shape cut to what a personal assistant needs; `asked` since rev 1.7), rendered ≤ 4,000 chars.
2. **One writer**: `working_state::update(previous, new lines) → state` — one prompt, one parser (`task_extraction::read_json_answer`, LQ13), one model key (`[orchestrator.costs] summary_model`), one usage label (`orchestrator_summary`) and its one existing daily ceiling. Three call sites: the loop's compaction tier, the turn-end lag refresh (today's `update_summary_background`), and the close.
3. **Compaction pays one call, not two**, on the summariser's model, and its output lands on the row at turn end with no second call (R1).
4. **The episode note is a projection** of the state at the close — no episode prompt, no episode call; MD-16's note is byte-for-byte the same shape, still found by search and the timeline, never by automatic recall, forgotten with its conversation. *(Reversed by CQ-11, rev 1.9: the note is written by its own summariser call over the conversation's rows at the close, under its own label `orchestrator_episode` and the summary ceiling — two summarisers, the state's writer and the episode's (§3.4).)*
5. **Delivery in the history layer**: the state takes `session.summary`'s slot and is exempt from the head-trim; a new conversation on the same lane and project reads the previous conversation's state live for its first three user turns, with an opt-out; the lead gets the state after its objective (R2).
6. **Visible**: the state is on the wire and in a chat-aside card; a "continuing from" line comes from one `done` datum in both clients.
7. **Measured**: a continuity split of the learning corpus (carry-over off vs on), an offline compaction invariant, and the episode split as a regression gate.
8. Model calls per conversation: `T1 = C + S′ + Q′ ≤ T0 − C` (§9; since CQ-11, rev 1.9, plus the summaries' own calls); no frozen memory contract is reversed (§7).

## 2. The continuity model

**`WorkingState`** (`crates/openalpaca_core/src/orchestrator/working_state.rs`, new; JSON in `session.working_state`):

```json
{"v":1,"topic":"3–8 words","goal":"what the user wants done, in their terms",
 "done":["established or finished, with files, artifacts, task ids"],
 "asked":["a question the user asked and had answered: its topic and the answer's gist"],
 "decisions":["chosen, turned down, changed"],
 "open":["unanswered or pending, the assistant's offers and questions not taken up included"],
 "next":"the work's next step as the user would state it, or \"\"","refs":["task 1a2b…","artifact reports/x.md"]}
```

*(Rev 1.7: `asked` is new (F3) — `#[serde(default)]`, so a state stored before it reads as one that asked nothing; the cut drops its items after `done`'s, with the lists and before `goal`; `open` and `next` say whose they are (F1).)*

Rendered by one function into the wrapped `<context_data type="working_state" trust="user_derived">` form (`orchestrator/mod.rs:273-285`), heading *"Working state of this conversation, as of <updated_at>"*; over `summary_max_chars` (4,000) it is cut list-item by list-item, `next` kept, never inside a character. Written in the user's language.

**Row** (`session`): `working_state TEXT NOT NULL DEFAULT ''`, `working_state_version INTEGER`, `working_state_through INTEGER` (the highest `conversation_messages.id` the state covers — **only rows the writer actually read**, §3.2), `working_state_updated_at TEXT`, `episode_note_id TEXT` (the last projected note's id; null until a close — since CQ-11, rev 1.9, the last written summary's). These replace `summary`, `summary_version`, `last_summarized_message_id`, `summary_updated_at` (`migrations/001_baseline.sql:196-214`). *(As built: the two counters are `INTEGER NOT NULL DEFAULT 0` (rev 1.5, slice 1 item 2), and a sixth column, `inherit INTEGER NOT NULL DEFAULT 1`, keeps CQ-5's per-session opt-out (rev 1.4 item 1, for the lead to ratify).)*

## 3. Write paths

**3.1 The writer.** `working_state::update(previous: Option<&WorkingState>, lines: &[TranscriptLine]) -> RouterRequest` and `parse(answer) -> Result<WorkingState, Unusable>`. Prompt committed as `working_state_prompt.txt` (pinned by a fixture test as `the_episode_prompt_matches_its_fixture` pins today's): *update the working state of this conversation; keep what the user settled, what is unfinished and the next step; keep names, ids, paths and dates exactly; write in the user's language; answer with one JSON object and nothing else.* Lines are `[user]`/`[assistant]`/`[tool]` rows, each cut to `msg_trunc_chars` (1,500), the same join the loop calls build today (`backend.rs:237-249`). *(Rev 1.7, as built: `next` is the work's next step as the user would state it, an offer or a question of the assistant's belongs in `open`, and rule 7 keeps a refused tool call, an approval not given or a limit the assistant met out of the state (F1); a line cut to `msg_trunc_chars` ends in ` …` and rule 5 says such a line was shortened, not cut off (F4); the close, the lag refresh and — on the main loop — compaction read the previous conversation's state, when the conversation was given it, under the heading `[carried from the previous conversation — not this conversation's work unless the user continued it]` ahead of its own lines, and rule 8 says to leave out what reached the conversation only through it (F2); no call site reads a row a forget suppressed, nor the rest of its turn (F5); a cut answer is read as chat learning's extraction reads one, LQ20 (f) (F7).)* Request: `model = summary_model` (unset → the router default, `routing/router/completion.rs:135-136`), `temperature 0`, `max_tokens 1536`, `thinking: Disabled` (M2), `RequestContext.agent_id = "orchestrator_summary"`, usage recorded under it (`summary.rs:111-201` kept), the daily cap `summary_max_daily_cost_usd` pre-checked at every site (`summary.rs:33-42`). A cut answer is reported cut and never rescued; an unusable answer at compaction falls back to `compress_context` as Phase 3 does today (`compaction.rs:90-106`); at turn end or close it leaves the row untouched.

**3.2 The cursor — rows the writer read, nothing else.** `build_context` (`orchestrator/context_builder.rs:30-174`) returns the ids of the rows it placed in the prompt (`ConversationContext.recent_row_ids`, oldest first); compose reports how many leading history messages the assembly trim removed (`compose/assembly.rs:66-90` → `history_head_dropped`); the compactor reports how many history messages lay inside `messages[2..boundary]` (`history_covered`). Then `through = recent_row_ids[head_dropped + covered − 1]` **when `head_dropped == 0`**; when the trim dropped head rows, `through` is not advanced past them (`through = recent_row_ids[0] − 1`, i.e. unchanged) — the lag refresh summarises them later when they scroll out, exactly as today's `last_summarized_message_id` does (panel defect U-2; a small-window case, never a lost row). The lag refresh's `through` = the last `older_window` id (`context_builder.rs:108-129`), as today. The close's `through` = the session's newest row.

**3.3 Compaction.** `CompactionPipeline::compact` (`context_budget/compaction.rs:49-108`) loses Phase 1: `MemoryExtractor`, `ExtractedMemory`, `CompactionResult.extracted_memories`, `CompactionReport.memories_extracted`, the `memories_extracted` keys of the log record (`mod.rs:686`) and of `SystemEvent::CompactionTriggered` (`mod.rs:703`; bridge arm `apps/openalpacad/src/event_bridge.rs:505-511`) go (CQ-1). ## 9. Cost

Per conversation with C compactions, S lag refreshes, Q closes with new user turns: today `T0 = 2C + S + Q` (compaction on the router default — the answering model on a local-only install — 1,024 + 2,048 output tokens, the older slice read twice; a close call only after 4 user turns); design `T1 = C + S′ + Q′` with `S′ ≤ S` (a compaction moves `through` to the tip of what it read) and `Q′ ≤ Q + (closes of short conversations that had no episode call before)`, one call each of 1,536 output tokens on `summary_model`. Worked: 10 user turns, no compaction → 1 vs 1; 30 turns, one compaction on a 32K model → 4 vs ≤ 3; 100 turns over three days, three compactions → 22 vs ≤ 16. Compaction input halves (one read of the slice); at compaction one call instead of two sequential ones. Every surviving call's output is read by something. *(Rev 1.9, CQ-11: a close is up to two calls — the refresh (in `Q′`) and, per window of at least four user turns past `episode_through`, the summary's own (`E`, at most 1,024 output tokens on `summary_model`, under `orchestrator_episode`) — so `T1 = C + S′ + Q′ + E`, `E` being the episode calls `T0` already counts in `Q`; what the design still saves is the compaction's second call and `S − S′`, against the new `Q′`: `T1 ≤ T0 − C + Q′`.
