## Problem
The generic tool-approval prompt shows a tool's `tool_arguments` to the human who approves or denies the call. None of the renderers neutralises Unicode format characters (Cf: bidi embeddings/overrides/isolates U+202A–202E and U+2066–2069, zero-width U+200B–200F, U+FEFF, the tag characters U+E0020–E007F, …), line/paragraph separators (U+2028/U+2029), or C1 controls (U+0080–U+009F). `serde_json` and `JSON.stringify` escape C0 controls inside strings but pass all of these through raw. A model-, MCP-server- or plugin-produced argument containing U+202E or a zero-width character can make the approval text read differently from what will actually run. This is the one surface where the human decides.

## Decision (binding; a reviewer may challenge it with evidence, an implementer may not silently change it)
1. **Visible escape, not drop.** On an approval surface every such character in tool-controlled text is rendered as `<U+XXXX>` — uppercase hex, zero-padded to at least four digits (`<U+202E>`, `<U+200B>`, `<U+009B>`, `<U+E0041>`). Why: the human must be told that something invisible is there. Dropping would show a benign-looking value that differs from the one that runs (a zero-width character inside a path, a filename, an allow-listed command); a visible escape is honest about the exact code points. The cost — an emoji zero-width joiner or a soft hyphen shows as an escape — is acceptable on a surface whose job is to be exact.
2. **The set** is `openalpaca_core::utils::text::is_hidden` (Cc ∪ Unicode 16 Cf, already pinned against the `regex` crate's `\p{Cf}` by a test) **plus U+2028 and U+2029**, **minus `\n` (U+000A) and `\t` (U+0009)**, which the renderers' own layout (pretty-printed JSON) uses. `\r` is escaped. Do not change `is_hidden` itself (R2's `one_line` depends on it); build the escaping function beside it.
3. **One notice line** when at least one character was escaped, the same wording on every surface, defined once in Rust and mirrored in TypeScript. Suggested: `Note: this request contains N hidden character(s), shown as <U+…>.` (singular/plural handled). Place it directly under the arguments.
4. **What is escaped:** every tool-controlled string a surface shows in the approval prompt — `tool_arguments` (after serialization), the **tool name** (MCP `<server>__<tool>` and plugin `<plugin>::<tool>` names come from third parties) and the **agent id** where shown. Not escaped: OpenAlpaca's own fixed wording, and the daemon-authored `preview` (already sanitized server-side by R2's `one_line`, which *drops* hidden characters — that choice stays: the preview is OpenAlpaca-composed prose for reading, and the exact values that will run are in the arguments, which this spec escapes). Document that distinction where the helper lives.
5. **Display only.** Nothing that is sent to the tool, stored, returned to the daemon or used to match a reply changes. The request id, the `/yes`–`/no` handling and every POST body are untouched.
6. **Truncation** (the connectors' 500-byte cut, and any other cut): escape first, then cut, never inside an escape sequence; the notice counts every escaped character of the full value, not only the part shown.
7. **One implementation per language.**
   - Rust: a public function in `crates/openalpaca_core/src/utils/text.rs` (it is already `pub`), used by the connectors and the CLI (both depend on `openalpaca_core`). Suggested shape: `pub fn escape_hidden(text: &str) -> Escaped` with the escaped text and the count, plus a notice helper; the implementer may choose a better shape.
   - TypeScript: one module in `apps/openalpaca-gui/src/lib/` (e.g. `hidden-chars.ts`) used by the GUI.
   - **Parity is pinned by a test on both sides**, e.g. a committed fixture of code-point ranges inside the GUI tree that the TS module derives its set from and a Rust test (reading the file via `CARGO_MANIFEST_DIR`) asserts `is_hidden(c) ∪ {U+2028, U+2029} ∖ {\n, \t}` equals over every scalar value. An equivalent mechanism is acceptable if it makes drift fail a test on either side.
8. **GUI rendering.** Escapes are visibly distinct (e.g. a styled span) but plain text: no HTML injection (React escapes; do not use `dangerouslySetInnerHTML`). The arguments block also gets `dir="ltr"` and `unicode-bidi: isolate` (or `plaintext`) so strong right-to-left letters, which are not format characters and stay as written, cannot reorder the surrounding card text. Keep the existing card layout.

## Tests first

## Owner question — the escape's delimiters (`S1-review-security-3.md` F1; answered)
- **Answered by the owner, 2026-09-26: keep the form.** `<U+XXXX>` stays on every surface, and nothing in the code changes. The question and the reasons below are kept as they were put.
- **The question.** The escape `<U+XXXX>` (item 1) is delimited by `<` and `>`, which are redirection operators in `sh`, the shell `shell_execute` runs, and the sanitizer allows both on purpose. On the plain-text surfaces — the chat connectors and the CLI — a literal escape-looking token typed into a shell command can be a live redirection that a person, taught that `<U+…>` means "one invisible character here", reads past.
- **What ships.** The plain-text form `<U+XXXX>` everywhere. Three things tell a real escape from a typed one: the notice's count, which a typed literal never raises (item 3, the recorded residue under A1–A4); on the GUI's card, bar, run card, resolution row, consent row and the Memory view's cards, the styled span, which a typed literal does not get; and in JSON (A9) the `\u` form, where a typed `<U+202E>` is plain text.
- **The alternative.** A delimiter pair that is not shell syntax, e.g. `⟨U+202E⟩` (U+27E8 / U+27E9 MATHEMATICAL LEFT/RIGHT ANGLE BRACKET), or the reviewer's option (a): write a literal `<` that begins `<U+` as `<U+003C>` and count it, so every `<U+…>` on any surface is a real escape. Either changes item 1's form (or adds a context rule) on every surface, the shared table's cases and every manual.
- **Recommendation: keep the form**, unless the owner wants a delimiter that is not shell syntax. The count and the GUI's styling already disambiguate, the attack needs a confirm-listed shell tool and model-controlled arguments, and a non-ASCII delimiter is harder to type and to search for in the CLI's and the connectors' plain text.
