# CLAUDE.md — OpenAlpaca

## Workflow Orchestration

### 1. Plan Node Default
- Enter plan mode for ANY non-trivial task (3+ steps or architectural decisions)
- If something goes sideways, STOP and re-plan immediately - don't keep pushing
- Use plan mode for verification steps, not just building
- Write detailed specs upfront to reduce ambiguity

### 2. Subagent Strategy
- Use subagents liberally to keep main context window clean
- Offload research, exploration, and parallel analysis to subagents
- For complex problems, throw more compute at it via subagents
- One tack per subagent for focused execution

### 3. Self-Improvement Loop
- After ANY correction from the user: update `tasks/lessons.md` with the pattern
- Write rules for yourself that prevent the same mistake
- Ruthlessly iterate on these lessons until mistake rate drops
- Review lessons at session start for relevant project

### 4. Verification Before Done
- Never mark a task complete without proving it works
- Diff behavior between main and your changes when relevant
- Ask yourself: "Would a staff engineer approve this?"
- Run tests, check logs, demonstrate correctness

### 5. Demand Elegance (Balanced)
- For non-trivial changes: pause and ask "is there a more elegant way?"
- If a fix feels hacky: "Knowing everything I know now, implement the elegant solution"
- Skip this for simple, obvious fixes - don't over-engineer
- Challenge your own work before presenting it

### 6. Autonomous Bug Fixing
- When given a bug report: just fix it. Don't ask for hand-holding
- Point at logs, errors, failing tests - then resolve them
- Zero context switching required from the user
- Go fix failing CI tests without being told how

## Task Management
1. **Plan First**: Write plan to `tasks/todo.md` with checkable items (`tasks/api-fix-plan.md` is the standing plan; `tasks/todo.md` tracks the active chunk and its review)
2. **Verify Plan**: Check in before starting implementation
3. **Track Progress**: Mark items complete as you go
4. **Explain Changes**: High-level summary at each step
5. **Document Results**: Add review section to `tasks/todo.md`
6. **Capture Lessons**: Update `tasks/lessons.md` after corrections

## Core Principles
- **Simplicity First**: Make every change as simple as possible. Impact minimal code.
- **No Laziness**: Find root causes. No temporary fixes. Senior developer standards.
- **Minimal Impact**: Changes should only touch what's necessary. Avoid introducing bugs.

### Execution Topology

The orchestrator dispatches workflows via `TaskDispatcher`. **Lead agent** (`dispatcher/lead_agent.rs`) is the only topology: a single orchestrating agent, spawned from an agent template with the `orchestration` capability (`config/agents/lead_agent.md`), delegates autonomously via `spawn_subagent` / `spawn_subagents_batch` (1–8 per call) / `wait_for_subagents` — batch spawning plus interruptible waiting is the parallel-work story. The lead's own surface also carries the installed MCP/plugin extension tools of every **enabled** extension and a per-request `invoke_skill`, so it can run integrations and catalog skills directly or delegate; subagents stay template-scoped (only their declared capabilities). A template grants capability names and the sandbox checks tool names, so both the lead and the subagent spawn path widen the template's allow list with the surface they resolved (`SandboxPolicy::admit_tool_surface`) — a subagent granted `web_access` may call `web_search`/`web_fetch`. The widening adds that surface and nothing else; the list still carries the capability strings and the check is a name match, so a registered tool *named* like a listed string is admitted as it always was. The legacy planner ladder, sequential pipeline, and DAG executor (and their `orchestrator.routing.mode = "planner"` rollback switch) were deleted in Routing V2 Phase 5.

### Message Routing (Routing V2)

`Orchestrator::handle_message_internal` (`orchestrator/handlers.rs`) routes each message through a short ladder:

1. **Deterministic tier** (no LLM): task ops (`/status`, `/tasks`, `/cancel|/pause|/resume` — bare control commands resolve against the lane's active workflows), the `/steer <msg>` steering override, and slash/router-selected skills.
2. **Social fast path** — exact-phrase match ("thanks", "ok"), answered before the main loop.
3. **Main loop** — everything else, *including while workflows run* (chat-by-default; lanes are never captured). `handle_simple_query` runs the agentic loop with the full persona/memory prompt and a per-request tool set: `start_workflow`, `task_status`, memory tools (`memory_store`/`memory_forget`/`memory_search`), plus `steer_workflow`/`queue_followup` while the lane has active workflows (`tools/builtins/main_loop.rs`). Chat vs. task vs. steer is the model's tool choice; a started workflow surfaces as structured `delegation{task_id, title}` on `HandleResult`/`GatewayResponse`/SSE `done`. **A turn never ends with nothing** (V3): a main-loop turn that finishes without answer text for any reason but `Cancelled` — `MaxRounds`, `CostExceeded`, a `Truncated` with nothing in it, `Error`, or a `Complete` the model wrote no words into — answers with `LoopResult::no_answer_line()`, one runtime-authored sentence naming the reason in the user's terms plus the last tool error (`LoopResult.last_tool_error`, capped at 600 bytes). It is the turn's content everywhere: persisted as the assistant row, sent as the one fallback delta, carried on `done.content`. An `Error` exit keeps `is_error` — the message changes, the failure signal does not. **A turn never claims a run it did not start** (round 13): a delegating assistant row replays into later history with one fixed provenance line (`orchestrator/context_builder.rs::delegation_provenance_line`, replay only — the stored row is untouched); the relay rules and `start_workflow`'s description say a run starts only through a call in this turn and that an explicit workflow request or an ask to write/save an artifact is that call; and `LoopConfig.answer_guard` (`runner/agentic_loop/answer_guard.rs`) reads the finished answer before it is returned — `RunClaimGuard` (`query_handler/run_claim_guard.rs`) rejects an answer that **states a task id nothing answers to** (round 15/N1: the predicate is three facts, not a reading of the sentence — no successful `start_workflow` this turn; a token in an id position that looks like an id, so a date or a bare number is never one; and no run **of this turn's owner** matching it — round 14/J1: `owner_has_task_id_prefix` over `created_by`, any lane), buys exactly one corrective round naming the id (N2), and if the id is still there **appends** one runtime line beneath the model's answer rather than replacing it (N3). A turn that really delegated, or that quotes an existing run of its owner, is untouched; a turn stating no id queries nothing.

The legacy planner ladder (the keyword-classified `ComplexTask`/`RememberCommand`/`ForgetCommand` intents, fast path, two-phase triage, hierarchical planner, replanner) and its `orchestrator.routing.mode` switch were deleted in Routing V2 Phase 5; the retired mode strings (`two_phase_*`, `planner_*`, `fast_path`, `no_llm`) survive only in historical telemetry rows. Memory writes/deletes are now the model's `memory_store`/`memory_forget` tool calls, not "remember ..." prefix commands.

Mid-workflow steering (gated on `steering_enabled`, default on): each running lead-agent task registers a `SteeringInbox` (`runner/steering.rs`) that the agentic loop drains at its round boundary and completion guard, injecting `<user_interjection>` messages. Workflow completion posts a model-authored completion report to the lane (template fallback for empty/budget exits); `queue_followup` items land in `lane_followups` and auto-start when the workflow finalizes (`followup_autostart`). See `docs/agent-loop.md` for the full contract.

### Extensibility: MCP + Plugins

Two mechanisms extend the tool surface:

- **MCP servers** (`config/mcp.toml`): the daemon connects out to declared MCP servers at boot (`openalpaca_mcp` crate, stdio or streamable-HTTP transports) and registers their tools in the tool registry as `<server>__<tool>`. Each imported tool provides a capability equal to its namespaced name, so agent templates select MCP tools by listing `<server>__<tool>` in `capabilities` (skills: `requires_capabilities`). Installed MCP/plugin tools are on the main loop's DEFAULT surface (both `tool_selection` modes), less those of an extension that is not `Enabled`. **There is no per-tool opt-out:** the old per-tool deny key under `execution.skill_defaults` was purged in C8 (design §11.1) — a boot-time `WARN` in `load_daemon_config` (`daemon_config/mod.rs`) is all that remains, for a hand-edited `daemon.toml` still carrying it. Tools only — MCP resources/prompts are stubbed (not implemented), and serving MCP is a non-goal. Per-server failures are logged, never fatal.
- **Plugins** (`~/.openalpaca/plugins/`): out-of-process child programs speaking JSON-RPC 2.0 over stdio, declared by a `plugin.toml` manifest, gated by a first-load approval flow (one `.permissions.toml` at the plugins root for all plugins; per-plugin config at `<root>/.config/<plugin>.toml`, per-plugin durable state at `<root>/.data/<plugin>/`, which survives an update; an uninstall *moves* the directory to `<root>/.trash/<plugin>-<ts>/` and never deletes what the owner dropped in). Management is the extension surface — `GET /v1/extensions`, `POST /v1/extensions/plugin` (install), `PUT|DELETE /v1/extensions/plugin/{id}` (update, uninstall/remove), the verb and config routes below, and `openalpaca ext …` / `openalpaca plugin …`. Plugin tools register as `<plugin>::<tool>`; plugins can also contribute skills and agent templates. Plugin-contributed skills (`SkillSource::Plugin`) are invokable like file-based skills (slash command or router selection): the orchestrator delegates to the plugin's `PluginSkillExecutor` out-of-process, proxying tool callbacks through the sandboxed execute path (`orchestrator/skill/invocation.rs`). Plugin-contributed agent templates (`AgentSource::Plugin`) execute through the lead-agent subagent spawn path: `runner/plugin_agent.rs` drives the plugin's external reasoning loop (spawn → step polls, 50-iteration cap) and proxies its tool requests through the sandboxed execute path. Connector and LLM-provider plugin bridges exist in code but are not yet wired into `ConnectorManager`/`LlmRouter` — treat those plugin types as non-functional.
- **Extension enable/disable is live** (N5, ADR-030 — design C1–C8): one ledger (`crates/openalpaca_core/src/tools/extensions/`) holds every extension's state; two supervisors own the lifecycles (`apps/openalpacad/src/managers/mcp/` for MCP, `crates/openalpaca_plugins/src/manager.rs` for plugins); the gate refuses a tool whose extension is not `Enabled` and announces the withholding instead of degrading silently. Routes (all of them, `apps/openalpacad/src/router.rs:332-364`): `GET /v1/extensions` (the list — there is no per-extension GET), `POST /v1/extensions/{kind}/{id}/{verb}` (`enable|disable|reload|approve|deny`), `GET|POST /v1/extensions/{kind}/{id}/config` (the GET redacts), `POST /v1/extensions/{kind}` (install), `POST /v1/extensions/plugin/validate` (dry run), `PUT|DELETE /v1/extensions/{kind}/{id}` (update, uninstall/orphan-row removal), plus the read-only catalogs `GET /v1/tools` and `GET /v1/skills` (+ `/v1/skills/health`). The `/v1/plugins*` routes and the `plugin_*` events are **gone** (C7); the event family is `extension_state_changed` / `extension_capability_withheld` / `extension_capability_withdrawn`. These routes use the design's flat `{"error":"<word>"}` envelope, not the shared `api_error` one (plan §7's single exception). CLI: `openalpaca ext list|info|enable|disable|reload|approve|deny|remove|install|update|uninstall|mcp add|mcp remove`, with `openalpaca plugin …` kept as the plugin-shaped shortcut over the same routes. GUI: Settings → Extensions and Settings → Tools.

## Key Patterns

### Async / Concurrency

- **Runtime**: tokio multi-thread (`#[tokio::main]` in both daemon and CLI)
- **Event bus**: `tokio::sync::broadcast` channel (`EventBus`) for system-wide events
- **Cancellation**: `tokio_util::sync::CancellationToken` per task, registered in `SharedContext.cancellation_tokens`. Checked at the top of every agentic-loop round.
- **Global LLM concurrency**: `tokio::sync::Semaphore` in `LlmRouter` caps in-flight API calls
- **Shutdown**: `tokio::sync::mpsc` channel in daemon `AppState`

### Hot-Reloadable Config

`Arc<ArcSwap<T>>` for lock-free reads:
- `DaemonConfig` — execution limits, server settings
- `LlmRouter.default_model` — default model ID
- `LlmRouter.runtime_config` — timeouts, endpoints
- Per-provider `KeyPool` — API keys

`Arc<RwLock<T>>` for persona documents: `system_persona`, `user_document`, `identity_document`.

### Error Handling

- **`thiserror`** for typed library errors: `LlmError`, `LlmRouterError`, `ConnectorError`, `KeyPoolError`
- **`anyhow`** for application-level code: storage, daemon startup, config loading
- **`Result<String, String>`** for orchestrator internal dispatch paths
- **Mutex poison recovery**: `lock().unwrap_or_else(|p| p.into_inner())` with `tracing::warn!`

### LLM Router Flow

1. Resolve the model against the catalogue **before** the call (`resolve_routable`, both paths): a requested model that is not routable walks the ladder — request `fallback_models` → the model's chain → `[orchestrator] fallback_models` → the default of the first loaded provider that has a routable one (empty/absent `default_model` → the first discovered model, preferring tool-capable). Every substitution is announced once per distinct (requested → effective) pair; nothing routable is `LlmRouterError::NoRoutableModel`, one error naming the fix, **not** "Unknown model" and not transient. `GET /v1/status`'s `llm` block carries `{default_model, default_model_routable, effective_default_model}`.
2. Acquire global concurrency semaphore
3. Resolve provider from `ModelRegistry`
4. Pick key via selection strategy (RoundRobin / LeastRecentlyUsed / PrimaryFallback) — **unless the provider needs no key** (`LlmProvider::requires_key()`, false only for Ollama): an empty pool then yields a synthetic keyless rate-limiter slot instead of `NoKeys`, in both the retry ladder and the streaming path. Never written to config, never in key health. A keyed provider with an empty pool is still refused.
5. Per-key rate limiter: concurrency + RPM/TPM token buckets + circuit breaker
6. On rate limit → try next key (max 2 wait cycles, 30s each)
7. On failure → model-level fallback chain (the same ladder) → CLI backend fallback (Claude Code CLI / Codex CLI)

**The model reported is the model that answered** (V4). `LlmRouter::complete_streaming` returns `RoutedStream { model, stream }` — the router is the only code that knows which rung of the ladder it settled on, and a stream carries no `model` of its own — so a caller takes `.stream` and reports `.model`; that id reaches `LoopResult.model_used`, the usage row, `LlmCallCompleted`, the conversation row, the session log and the SSE `done`, and it is the id the cost tracker prices against. The requested id may be logged beside it, never in its place. `POST /v1/chat`'s `model_used` is a *prediction* (the POST returns before the turn runs): `effective_default_model()` for a turn that names no model, `null` when nothing is routable.

Around the flow: **discovery** (`refresh_models_for(&ProviderType)`) asks each provider what it can serve — for Ollama, its native `GET /api/tags` + `POST /api/show` (not the OpenAI-compatible route), registering each chat model at price 0 with the real context window (8192 fallback), `supports_image` from `vision`, `supports_tools` from `tools`; embedding-only models are skipped and a vanished tag is withdrawn (a `[models]` row is un-discovered, never deleted). It needs no key and runs at boot, on the enable toggle, on a hot reload and on `POST /v1/models/refresh`. **Cost** prices from the router's live `Arc<ModelRegistry>` (`CostTracker::use_registry`), so a discovered local model is 0 and a `[models]` price is honoured. **Timeouts** resolve through `LlmRuntimeConfig::request_timeout_for(provider)` (`[providers.<name>] request_timeout_secs` → `[timeouts] llm_request_timeout_secs` → 120s, clamped 1..=86400s) and apply to non-streaming calls only — the client built by `providers::build_http_client` has no total deadline, only a connect bound and an idle `read_timeout`, so a healthy stream is never cut.

### State Persistence

`TaskRepository::update_state()` uses optimistic locking (`state_version` column). On version conflict, callers retry with linear backoff plus pseudo-jitter (10ms + 5ms/attempt + task-id-derived jitter, max 3 attempts — `dispatcher/outcome.rs`).

### Storage

Single SQLite connection wrapped in `Arc<Mutex<Connection>>`. WAL mode, `busy_timeout=5000ms`. **The unreleased 001–042 migration chain is squashed into one baseline.** `migrations::MIGRATIONS` holds exactly one entry — `Migration { version: 42, name: "baseline", sql: include_str!("001_baseline.sql") }` — and `BASELINE_VERSION` is that entry's version (`crates/openalpaca_storage/src/migrations/mod.rs:15-22`). The file creates the chain's **final** schema in one pass and registers itself: its last statement is `INSERT INTO schema_version(version) VALUES (42);` (`001_baseline.sql:559`) — `run_migrations` executes a migration's SQL and nothing else, so every migration writes its own version row. Three cases at open (`run_migrations`, `database/mod.rs:112-148`): a fresh database (version 0) gets the baseline; one already at 42 has no pending migration and returns early; one at **1..41 is refused (`:127-138`) before any migration runs**, so its schema and rows survive for an export under an older build — the baseline creates the final schema and cannot upgrade a partly-migrated development database. **To add migration 43:** drop a new `.sql` file in `crates/openalpaca_storage/src/migrations/` — the loader reads the registry, not the directory, so the file name is free; name it for the version it registers (`043_<name>.sql`) — append a `Migration { version: 43, … }` entry to `MIGRATIONS`, and end the SQL with `INSERT INTO schema_version(version) VALUES (43);`. Then move the three assertions that read a *fresh* database's version off `BASELINE_VERSION` (`database/tests.rs:11`, `:34`, `:50` — the last asserts the whole `schema_version` list): `BASELINE_VERSION` stays 42 and goes on meaning "oldest openable schema", which is what `:59`'s refusal test reads it as. The file's first `--` comment becomes its summary in the generated `docs/api/database/` docs (`python3 scripts/gen_api_docs.py`). Comments and docs across the tree still cite the old numbers ("migration 041", `039_sessions.sql`) as provenance for when a column or index arrived; those are true as history and the files are in git, but nothing resolves them in the tree any more. `lane_followups.unattended` and `task.unattended` (both `INTEGER NOT NULL DEFAULT 0`) preserve the "nobody here can answer a confirmation" declaration for parked work. `tool_execution_log` and `skill_execution_log` each have a `timestamp`-leading index; the two "today" counts behind `GET /v1/tools` / `GET /v1/skills` name them with `INDEXED BY` because the planner otherwise prefers the grouping index and scans. Memory search is hybrid: FTS5 full-text + sqlite-vec 768-dim KNN with cascading scope (workspace → global).

Data directory: `~/.openalpaca/` (all platforms — `store::home_root()`, overridable with `OPENALPACA_HOME_STORE`; absolute paths only). `state/` holds `openalpaca.db` (+ `-wal`/`-shm`), `discovery.json`, `openalpacad.lock`, `.master_key`, `backups/`, `logs/` (`daemon.log`, `gui.log`), `cache/fastembed` (the ~1 GB local embedding model, created on demand by `store::embedding_cache_dir()` — regenerable; not the root-level content `cache/` below); `assets/` exists only on a machine whose uploads predate D2 — nothing writes there and nothing moves what is there; `config/` holds the runtime config the GUI- and CLI-managed daemons are started with; `plugins/` (dropped plugin dirs + `.permissions.toml`, `.config/<name>.toml`, `.data/<name>/`), `artifacts/`, `uploads/` and `sessions/` sit at the root, with `memory/`, `skills/`, `scratch/`, `cache/` reserved and uncreated. A project store is `<project>/.openalpaca/` and holds content only — `artifacts/` (heads committable, `.versions/` git-ignored), `uploads/`, and the rest reserved; session logs always live in the home store, never in a project. Each root is self-describing: `ensure_store()` seeds a `README.md` with a retention class per entry plus `.layout` (version, and `install_id` on the home root). A development build's data at `~/Library/Application Support/OpenAlpaca` (macOS) / `~/.local/share/openalpaca` (Linux) is **not** moved here — see the D1 bullet above and `crates/openalpaca_storage/src/store/legacy_root.rs`.

## Gotchas

- `.gitignore`'s `# Markdown Documentation (Except Manuals)` block blanket-ignores `*.md`. A new doc is invisible to git until whitelisted with a `!path` line — in that block, or in the `# UI rework reference docs` block near the end of the file; confirm with `git check-ignore -q <file>` (exit 0 = still ignored) before calling it committed. Cite the blocks by those comment headers, never by line number: the numbers have moved twice.
- `SystemEvent` and `ServerEvent` are matched exhaustively with no catch-all: a new variant needs an arm in `apps/openalpacad/src/event_bridge.rs:30` (system) or `apps/openalpacad/src/events/persistence.rs:12` (server) in the same commit.
- **A streamed frame yields every event it carries** (V1). The OpenAI-compatible parser (`crates/openalpaca_llm/src/providers/openai/streaming.rs`, shared by every OpenAI-compatible base — Ollama included) decodes a frame into a `Vec<StreamEvent>` and drains that queue before reading the next line; one `return` per matching field was the bug class, not one bad arm. Ollama puts a whole tool call — `id`, `name` **and** `arguments` — in a single frame, and returning at `id` dropped the arguments, which made every main-loop tool call arrive empty. Any new test for an OpenAI-compatible stream must include that shape (single-frame tool call; two tool calls in one frame; content + tool calls in one frame; tool calls + `finish_reason` in one frame), not just the split-frame shape OpenAI itself sends.
- Oversized tool results: a loop **with** a session log spills the whole result to `sessions/<id>/results/` and hands the model a stub — the first 2 KB plus `result_ref=file:results/…` — which the scoped `read_result` builtin pages back in; a loop **without** one — any caller that leaves `LoopConfig.session_log` at `None`, which is every non-session caller — falls back to an inline cut at the same threshold — one number, `[orchestrator.sessions] tool_result_inline_bytes`, default 32 KB (`MAX_TOOL_RESULT_SIZE`, `crates/openalpaca_core/src/runner/agentic_loop/tool_helpers.rs:4`). An `Err` result stays inline but cuts head+tail, so a compiler or test failure keeps the assertion at the end (`head_tail_tool_result`). `read_result` is offered wherever a spill can happen (R84): on the main loop's per-request surface when this daemon has a session log **and** a database (`tools/builtins/main_loop.rs`), on the lead's hand-assembled surface when the lead's own template grants it (`runner/lead_agent/mod.rs`, the `artifact_write` shape), and all nine shipped `config/agents/*.md` templates grant the capability. It is still a **grant, not ambient** — the constructor-appended set is untouched (owner decision T15 pending), so an agent whose template does not name `read_result` is refused it and reads a stub it cannot follow.
- `config/llm.toml` is seeded on first daemon start and is absent from a fresh checkout: without provider keys nothing can call a model, so the live steer eval and plan pre-check (d) need them — **except** a local Ollama, which needs no key at all (`[providers.ollama] enabled = true` and a pulled model is the whole setup; see `docs/Installation_Manual.md` → Local Models).
- Any test that enables Ollama must point at a mock or an unbindable port — `crate::test_util::MockOllama` (daemon, `#[cfg(test)]`) or `test_support::MockHttpServer` (`openalpaca_llm`, crate-private). Discovery is no longer gated on a key, so a fixture still naming `http://localhost:11434/v1` reaches whatever the developer's machine has installed and the assertions become machine-dependent (`hot_reload/llm_dedup_tests.rs` and `provider_enabled_tests.rs` use `http://127.0.0.1:1/v1` for exactly this).
- **`event_log` grows forever; nothing prunes it** (W6, verified — do not read this as a request to build a sweeper). Two writers: `EventBroadcaster::persist` (`apps/openalpacad/src/events/persistence.rs`) writes a row for **every** `ServerEvent` but `heartbeat` — 32 arms, `task_status`/`workflow_*`/`tool_*`/`extension_*` among them — and the security sandbox writes `security_violation`, `tool_auto_approved` and `tool_approval_unavailable` (`crates/openalpaca_core/src/security/sandbox/mod.rs:247`, `:509`). The sandbox half is new in practice: before V2 wired a database into the production sandboxes, `SandboxManager::with_db` had no production caller and those rows existed only in tests. The one periodic sweep, `background::spawn_telemetry_cleanup`, is `SkillExecutionRepository::cleanup_old(90, 7)` — `skill_execution_log` and `tool_execution_log` only, never `event_log`. `event_log` rows go away in exactly two places, both deliberate and neither periodic: a factory reset (`openalpaca config reset --factory` deletes the database file outright — `Database::factory_reset` and its 29 `DELETE`s are gone) and a project purge (`POST /v1/workspaces/purge` → `artifacts/mod.rs:1892`, which deletes the rows of that workspace's runs by `task_id`). Readers are `GET /v1/events/history` and `dispatcher/outcome.rs:156`. Whether the table needs a retention pass is nobody's default to adopt.
- `bun run check` is not `bun run build`: `tsc --noEmit` passed a `.test.tsx` object literal missing two required fields that `tsc -b` rejected. Run all four GUI gates, not the first one.
- macOS BSD `sed`: no `\b`, and `-i` needs `''`. Use `perl -pi -e` or a Python script for regex edits, and assert each anchor matches exactly once.
- Commit style: conventional prefixes (`docs:`, `docs(lessons):`, `fix:`, `feat:`); substantial commits end with a line naming what was verified; design docs carry a `rev N` status line and a revision log — bump both on every edit.
