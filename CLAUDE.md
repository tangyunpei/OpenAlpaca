# CLAUDE.md — OpenAlpaca

## Workflow Orchestration

### 1. Plan Node Default
- Enter plan mode for ANY non-trivial task (3+ steps or architectural decisions)
- If something goes sideways, STOP and re-plan immediately - don't keep pushing
- Use plan mode for verification steps, not just building
- Write detailed specs upfront to reduce ambiguity

### 2. Subagent Strategy
- Use subagents liberally to keep main context window clean
- Offload research, exploration, and parallel analysis to subagents
- For complex problems, throw more compute at it via subagents
- One tack per subagent for focused execution

### 3. Self-Improvement Loop
- After ANY correction from the user: update `tasks/lessons.md` with the pattern
- Write rules for yourself that prevent the same mistake
- Ruthlessly iterate on these lessons until mistake rate drops
- Review lessons at session start for relevant project

### 4. Verification Before Done
- Never mark a task complete without proving it works
- Diff behavior between main and your changes when relevant
- Ask yourself: "Would a staff engineer approve this?"
- Run tests, check logs, demonstrate correctness

### 5. Demand Elegance (Balanced)
- For non-trivial changes: pause and ask "is there a more elegant way?"
- If a fix feels hacky: "Knowing everything I know now, implement the elegant solution"
- Skip this for simple, obvious fixes - don't over-engineer
- Challenge your own work before presenting it

### 6. Autonomous Bug Fixing
- When given a bug report: just fix it. Don't ask for hand-holding
- Point at logs, errors, failing tests - then resolve them
- Zero context switching required from the user
- Go fix failing CI tests without being told how

## Task Management
1. **Plan First**: Write plan to `tasks/todo.md` with checkable items (`tasks/api-fix-plan.md` is the standing plan; `tasks/todo.md` tracks the active chunk and its review)
2. **Verify Plan**: Check in before starting implementation
3. **Track Progress**: Mark items complete as you go
4. **Explain Changes**: High-level summary at each step
5. **Document Results**: Add review section to `tasks/todo.md`
6. **Capture Lessons**: Update `tasks/lessons.md` after corrections

## Core Principles
- **No Laziness**: Find root causes. No temporary fixes. Senior developer standards.
- **Minimal Impact**: Changes should only touch what's necessary. Avoid introducing bugs. 
- **No compromise on migrations** (owner, 2026-10-12; overrides Minimal Impact for this work): when the toolchain, dependency and modernization programme (`tasks/deps-upgrade/`) moves to a new Rust, Tauri or React API or feature, it moves fully — no hold kept for convenience, no "not now" where the new form is available, no shim, partial adoption or older API form beside the new one. A real blocker (a dependency pinning an old major, the seven-day freshness rule DU-23) is named with its way out, never accepted silently. Safety rules and settled product decisions are not compromises and stay.

### Execution Topology

The orchestrator dispatches workflows via `TaskDispatcher`. **Lead agent** (`dispatcher/lead_agent.rs`) is the only topology: a single orchestrating agent, spawned from an agent template with the `orchestration` capability (`config/agents/lead_agent.md`), delegates autonomously via `spawn_subagent` / `spawn_subagents_batch` (1–8 per call) / `wait_for_subagents` — batch spawning plus interruptible waiting is the parallel-work story. The lead's own surface also carries `file_read`, `file_list` and `artifact_read` (in code — the storage design's R42: it reads the project and its by-products, and delegates the files a job is to produce), the installed MCP/plugin extension tools of every **enabled** extension and a per-request `invoke_skill`, so it can run integrations and catalog skills directly or delegate; subagents stay template-scoped (only their declared capabilities). A template grants capability names and the sandbox checks tool names, so both the lead and the subagent spawn path widen the template's allow list with the surface they resolved (`SandboxPolicy::admit_tool_surface`) — a subagent granted `web_access` may call `web_search`/`web_fetch`. The widening adds that surface and nothing else; the list still carries the capability strings and the check is a name match, so a registered tool *named* like a listed string is admitted as it always was. The legacy planner ladder, sequential pipeline, and DAG executor (and their `orchestrator.routing.mode = "planner"` rollback switch) were deleted in Routing V2 Phase 5.

### Message Routing (Routing V2)

`Orchestrator::handle_message_internal` (`orchestrator/handlers.rs`) routes each message through a short ladder:

1. **Deterministic tier** (no LLM): task ops (`/status`, `/tasks`, `/cancel|/pause|/resume` — bare control commands resolve against the lane's active workflows), the chat memory commands `/remember`, `/forget`, `/memories` (`Intent::MemoryCommand`, `orchestrator/memory_commands.rs`, MD-13 — matched before any skill, answered on attended app/CLI turns only, a fixed refusal everywhere else; their names are reserved from skills), the `/steer <msg>` steering override, and slash/router-selected skills.
2. **Social fast path** — exact-phrase match ("thanks", "ok"), answered before the main loop.
3. **Main loop** — everything else, *including while workflows run* (chat-by-default; lanes are never captured). `handle_simple_query` runs the agentic loop with the full persona/memory prompt and a per-request tool set: `start_workflow`, `task_status`, the three memory writers (`memory_store`/`memory_update`/`memory_forget`) and, on an attended `gui` turn, `memory_confirm` (MD-12), beside the globally registered read tools (`memory_search`/`memory_read`/`memory_list`/`memory_timeline`), plus `steer_workflow`/`queue_followup` while the lane has active workflows, `artifact_read` on every turn with a database, `file_read` on every project turn with `file_list` wherever `file_read` is, and `file_edit` beside a keyword-suggested `file_write` on a project turn (`tools/builtins/main_loop.rs`, and the query handler's offers from one project-turn predicate, `builtins::is_project_turn`; the storage design's R42, R48, rulings R-T6, R-T14). Each turn's context names the folder its file tools and shell act in, in one `<working_folder>` line naming only the tools the turn holds (R28, R-T22), the last line of the relay rules' message. A turn whose surface carries `memory_search` gets a three-line `<memory_rules>` system block (search answers an index; read the ids you need, several at once; since LQ19, before saving a fact about the user that changes an earlier one, search for the note it changes and name it in `supersedes` or by its `fact_key`; and, since the continuity design, a `previous_conversation` block names the note that records it — `memory_read` it when the user continues that work), and a turn offering `memory_confirm` gets a `<memory_suggestions>` block of up to three pending suggestions at the end of its memory message (quoted data, not a system block). The history layer starts with the conversation's **working state** (design 11, `orchestrator/working_state.rs`) as `<context_data type="working_state">` — the one message the assembly's head-trim never takes — and, while a new conversation on the lane and project has no state of its own and fewer than `carry_over_turns` (3) user turns and was not started fresh (`inherit: false`), with the previous conversation as `<context_data type="previous_conversation">`: its state, its last exchange, and the note that records it (Gotchas). The turn's `done` says whether its compaction wrote the state (`working_state_updated`) and which conversation's block the request carried (`continued_from: {session_id, topic}`, else `null`); a workflow's lead gets the chat's state after its objective. Chat vs. task vs. steer is the model's tool choice; a started workflow surfaces as structured `delegation{task_id, title}` on `HandleResult`/`GatewayResponse`/SSE `done`. **A turn never ends with nothing** (V3): a main-loop turn that finishes without answer text for any reason but `Cancelled` — `MaxRounds`, `CostExceeded`, a `Truncated` with nothing in it, `Error`, or a `Complete` the model wrote no words into — answers with `LoopResult::no_answer_line()`, one runtime-authored sentence naming the reason in the user's terms plus the last tool error (`LoopResult.last_tool_error`, capped at 600 bytes). It is the turn's content everywhere: persisted as the assistant row, sent as the one fallback delta, carried on `done.content`. An `Error` exit keeps `is_error` — the message changes, the failure signal does not. **A turn never claims a run it did not start** (round 13): a delegating assistant row replays into later history with one fixed provenance line (`orchestrator/context_builder.rs::delegation_provenance_line`, replay only — the stored row is untouched — and appended once: a row that already ends with its line replays as stored, Round G's G3b); the relay rules and `start_workflow`'s description say a run starts only through a call in this turn and that an explicit workflow request is that call, and — since the storage design's Stage 2 — the relay rules alone say that writing, editing or running a command in the project is the chat's own when those tools are on its surface, a file asked for with no writing tool on the surface being `start_workflow`'s (R-T7); and `LoopConfig.answer_guard` (`runner/agentic_loop/answer_guard.rs`) reads the finished answer before it is returned — `RunClaimGuard` (`query_handler/run_claim_guard.rs`) rejects an answer that **states a task id nothing answers to** (round 15/N1: the predicate is three facts, not a reading of the sentence — no successful `start_workflow` this turn; a token in an id position that looks like an id, so a date or a bare number is never one; and no run **of this turn's owner** matching it — round 14/J1: `owner_has_task_id_prefix` over `created_by`, any lane), buys exactly one corrective round naming the id (N2), and if the id is still there **appends** one runtime line beneath the model's answer rather than replacing it (N3). A turn that really delegated, or that quotes an existing run of its owner, is untouched; a turn stating no id queries nothing.

The legacy planner ladder (the keyword-classified `ComplexTask`/`RememberCommand`/`ForgetCommand` intents, fast path, two-phase triage, hierarchical planner, replanner) and its `orchestrator.routing.mode` switch were deleted in Routing V2 Phase 5; the retired mode strings (`two_phase_*`, `planner_*`, `fast_path`, `no_llm`) survive only in historical telemetry rows. Memory writes/deletes are the model's `memory_store`/`memory_update`/`memory_forget` tool calls or the typed `/remember`/`/forget` commands (deterministic, no model — a user-directed surface, origin `user`), not "remember ..." prefix commands — and a tool call is never a user-directed surface (only the person's Approve on `memory_confirm`'s card confirms, for that one write): it records origin `extracted_user` at most, cannot confirm a candidate, and cannot archive a note the user wrote (G2); since LQ11 its replacement or content edit of a note the user saved — origin `user`, `external` or `imported` — is written as a **suggestion** the person confirms, never applied, and refused only in the cases the Gotchas bullet on LQ11 lists.

Mid-workflow steering (gated on `steering_enabled`, default on): each running lead-agent task registers a `SteeringInbox` (`runner/steering.rs`) that the agentic loop drains at its round boundary and completion guard, injecting `<user_interjection>` messages. Workflow completion posts a model-authored completion report to the lane (template fallback for empty/budget exits); `queue_followup` items land in `lane_followups` and auto-start when the workflow finalizes (`followup_autostart`). See `docs/agent-loop.md` for the full contract.

### Extensibility: MCP + Plugins

Two mechanisms extend the tool surface:

- **MCP servers** (`config/mcp.toml`): the daemon connects out to declared MCP servers at boot (`openalpaca_mcp` crate, stdio or streamable-HTTP transports) and registers their tools in the tool registry as `<server>__<tool>`. Each imported tool provides a capability equal to its namespaced name, so agent templates select MCP tools by listing `<server>__<tool>` in `capabilities` (skills: `requires_capabilities`). Installed MCP/plugin tools are on the main loop's DEFAULT surface (both `tool_selection` modes), less those of an extension that is not `Enabled`. **There is no per-tool opt-out:** the old per-tool deny key under `execution.skill_defaults` was purged in C8 (design §11.1) — a boot-time `WARN` in `load_daemon_config` (`daemon_config/mod.rs`) is all that remains, for a hand-edited `daemon.toml` still carrying it. Tools only — MCP resources/prompts are stubbed (not implemented), and serving MCP is a non-goal. Per-server failures are logged, never fatal. A streamable-HTTP server's client is bounded by idleness, never by a total deadline (`crates/openalpaca_mcp/src/transport/http.rs`, N-MCP-2): a connect bound (the shorter of 30 s and `request_timeout_secs`) and an idle bound reset by every byte (the longer of 5 min and `request_timeout_secs`), so a streamed answer or a held-open GET stream is never cut while bytes arrive; a call's own deadline is still `request_timeout_secs` (default 30). A redirect is followed only on the server's own origin (scheme, host, port), up to ten hops, and only for a server with no `auth` or `extra_headers` (D6 (a)); a refused one is `McpError::RedirectRefused` — at bring-up the row reads `Failed` with `config_invalid`, its detail naming the target origin, and a call returns it at once, never retried — so a server whose `url` relies on a redirect (http→https included, or any redirect with credentials configured) stops connecting until `url` is the canonical endpoint.
- **Plugins** (`~/.openalpaca/plugins/`): out-of-process child programs speaking JSON-RPC 2.0 over stdio, declared by a `plugin.toml` manifest, gated by a first-load approval flow (one `.permissions.toml` at the plugins root for all plugins; per-plugin config at `<root>/.config/<plugin>.toml`, per-plugin durable state at `<root>/.data/<plugin>/`, which survives an update; an uninstall *moves* the directory to `<root>/.trash/<plugin>-<ts>/` and never deletes what the owner dropped in). Management is the extension surface — `GET /v1/extensions`, `POST /v1/extensions/plugin` (install), `PUT|DELETE /v1/extensions/plugin/{id}` (update, uninstall/remove), the verb and config routes below, and `openalpaca ext …` / `openalpaca plugin …`. Plugin tools register as `<plugin>::<tool>`; plugins can also contribute skills and agent templates. Plugin-contributed skills (`SkillSource::Plugin`) are invokable like file-based skills (slash command or router selection): the orchestrator delegates to the plugin's `PluginSkillExecutor` out-of-process, proxying tool callbacks through the sandboxed execute path (`orchestrator/skill/invocation.rs`). Plugin-contributed agent templates (`AgentSource::Plugin`) execute through the lead-agent subagent spawn path: `runner/plugin_agent.rs` drives the plugin's external reasoning loop (spawn → step polls, 50-iteration cap) and proxies its tool requests through the sandboxed execute path. Connector and LLM-provider plugin bridges exist in code but are not yet wired into `ConnectorManager`/`LlmRouter` — treat those plugin types as non-functional.
- **Extension enable/disable is live** (N5, ADR-030 — design C1–C8): one ledger (`crates/openalpaca_core/src/tools/extensions/`) holds every extension's state; two supervisors own the lifecycles (`apps/openalpacad/src/managers/mcp/` for MCP, `crates/openalpaca_plugins/src/manager.rs` for plugins); the gate refuses a tool whose extension is not `Enabled` and announces the withholding instead of degrading silently. Routes (all of them, `apps/openalpacad/src/router.rs:332-364`): `GET /v1/extensions` (the list — there is no per-extension GET), `POST /v1/extensions/{kind}/{id}/{verb}` (`enable|disable|reload|approve|deny`), `GET|POST /v1/extensions/{kind}/{id}/config` (the GET redacts), `POST /v1/extensions/{kind}` (install), `POST /v1/extensions/plugin/validate` (dry run), `PUT|DELETE /v1/extensions/{kind}/{id}` (update, uninstall/orphan-row removal), plus the read-only catalogs `GET /v1/tools` and `GET /v1/skills` (+ `/v1/skills/health`). The `/v1/plugins*` routes and the `plugin_*` events are **gone** (C7); the event family is `extension_state_changed` / `extension_capability_withheld` / `extension_capability_withdrawn`. These routes use the design's flat `{"error":"<word>"}` envelope, not the shared `api_error` one (plan §7's single exception). CLI: `openalpaca ext list|info|enable|disable|reload|approve|deny|remove|install|update|uninstall|mcp add|mcp remove`, with `openalpaca plugin …` kept as the plugin-shaped shortcut over the same routes. GUI: Settings → Extensions and Settings → Tools.

## Key Patterns

### Async / Concurrency

- **Runtime**: tokio multi-thread (`#[tokio::main]` in both daemon and CLI)
- **Event bus**: `tokio::sync::broadcast` channel (`EventBus`) for system-wide events
- **Cancellation**: `tokio_util::sync::CancellationToken` per task, registered in `SharedContext.cancellation_tokens`. Checked at the top of every agentic-loop round.
- **Global LLM concurrency**: `tokio::sync::Semaphore` in `LlmRouter` caps in-flight API calls
- **Shutdown**: `POST /v1/command {"command":"shutdown"}` sends on a `tokio::sync::mpsc` channel in `AppState` (`shutdown_tx`); it and SIGINT/SIGTERM converge on one `CancellationToken`, also held as `AppState.cancel_token` so the two long-lived bodies end on it (the events socket: a `daemon_shutting_down` frame, then close 1001; the chat SSE body: one `error` frame). `FORCE_EXIT_GRACE` (10 s, `apps/openalpacad/src/main.rs:71`) bounds the tail. Anything waiting for a daemon to be gone uses `openalpaca_storage::daemon_lifecycle` — process, then lock, never the port

### Hot-Reloadable Config

`Arc<ArcSwap<T>>` for lock-free reads:
- `DaemonConfig` — execution limits, server settings
- `LlmRouter.default_model` — default model ID
- `LlmRouter.runtime_config` — timeouts, endpoints
- Per-provider `KeyPool` — API keys

`Arc<RwLock<T>>` for persona documents: `system_persona`, `user_document`, `identity_document`.

### Error Handling

- **`thiserror`** for typed library errors: `LlmError`, `LlmRouterError`, `ConnectorError`, `KeyPoolError`
- **`anyhow`** for application-level code: storage, daemon startup, config loading
- **`Result<String, String>`** for orchestrator internal dispatch paths
- **Mutex poison recovery**: `lock().unwrap_or_else(|p| p.into_inner())` with `tracing::warn!`

### LLM Router Flow

1. Resolve the model against the catalogue **before** the call (`resolve_routable`, both paths): a requested model that is not routable walks the ladder — request `fallback_models` → the model's chain → `[orchestrator] fallback_models` → the default of the first loaded provider that has a routable one (empty/absent `default_model` → the first discovered model, preferring tool-capable). Every substitution is announced once per distinct (requested → effective) pair; nothing routable is `LlmRouterError::NoRoutableModel`, one error naming the fix, **not** "Unknown model" and not transient. `GET /v1/status`'s `llm` block carries `{default_model, default_model_routable, effective_default_model}`.
2. Acquire global concurrency semaphore
3. Resolve provider from `ModelRegistry`
4. Pick key via selection strategy (RoundRobin / LeastRecentlyUsed / PrimaryFallback) — **unless the provider needs no key** (`LlmProvider::requires_key()`, false only for Ollama): an empty pool then yields a synthetic keyless rate-limiter slot instead of `NoKeys`, in both the retry ladder and the streaming path. Never written to config, never in key health. A keyed provider with an empty pool is still refused.
5. Per-key rate limiter: concurrency + RPM/TPM token buckets + circuit breaker
6. On rate limit → try next key (max 2 wait cycles, 30s each)
7. On failure → model-level fallback chain (the same ladder) → CLI backend fallback (Claude Code CLI / Codex CLI)

**The model reported is the model that answered** (V4). `LlmRouter::complete_streaming` returns `RoutedStream { model, stream }` — the router is the only code that knows which rung of the ladder it settled on, and a stream carries no `model` of its own — so a caller takes `.stream` and reports `.model`; that id reaches `LoopResult.model_used`, the usage row, `LlmCallCompleted`, the conversation row, the session log and the SSE `done`, and it is the id the cost tracker prices against. The requested id may be logged beside it, never in its place. `POST /v1/chat`'s `model_used` is a *prediction* (the POST returns before the turn runs): `effective_default_model()` for a turn that names no model, `null` when nothing is routable.

Around the flow: **discovery** (`refresh_models_for(&ProviderType)`) asks each provider what it can serve — for Ollama, its native `GET /api/tags` + `POST /api/show` (not the OpenAI-compatible route), registering each chat model at price 0 with the real context window (8192 fallback), `supports_image` from `vision`, `supports_tools` from `tools`; embedding-only models are skipped and a vanished tag is withdrawn (a `[models]` row is un-discovered, never deleted). It needs no key and runs at boot, on the enable toggle, on a hot reload and on `POST /v1/models/refresh`. **Cost** prices from the router's live `Arc<ModelRegistry>` (`CostTracker::use_registry`), so a discovered local model is 0 and a `[models]` price is honoured. **Timeouts** resolve through `LlmRuntimeConfig::request_timeout_for(provider)` (`[providers.<name>] request_timeout_secs` → `[timeouts] llm_request_timeout_secs` → 120s, clamped 1..=86400s) and apply to non-streaming calls only — the client built by `providers::build_http_client` has no total deadline, only a connect bound and an idle `read_timeout`, so a healthy stream is never cut.

### State Persistence

`TaskRepository::update_state()` uses optimistic locking (`state_version` column). On version conflict, callers retry with linear backoff plus pseudo-jitter (10ms + 5ms/attempt + task-id-derived jitter, max 3 attempts — `dispatcher/outcome.rs`).

### Storage

Single SQLite connection wrapped in `Arc<Mutex<Connection>>`. WAL mode, `busy_timeout=5000ms`. No SQLite extension is loaded — `sqlite-vec` and its `ensure_vec_extension` are gone (memory redesign 3.5/3.6). **The unreleased migration chain is squashed into one baseline, and since the store revision (SQ-1, 2026-09-28) a migration's file number is its schema version: `001_baseline.sql` registers 1, the continuity design's `002_working_state.sql` (CQ-9) registers 2, the storage design's `003_no_project_store_rows.sql` (R25) registers 3, and its `004_project_files.sql` (ST-12, R35) registers 4.** `migrations::MIGRATIONS` (`crates/openalpaca_storage/src/migrations/mod.rs:23-44`) holds four entries, 1 `baseline`, 2 `working_state`, 3 `no_project_store_rows` and 4 `project_files`, and `BASELINE_VERSION` is the first entry's version, 1 (`:49`). The baseline creates the whole schema in one pass — the development history 001–045 squashed, Learning v2's `conversation_messages.request_id` and `.workspace_root` and the six-column `learning_cursor` included, with no cursor row seeded (a session with no row reads as the zero cursor, `repository/learning_cursor.rs`) — **without** the SQL memory engine (`memory`, `memory_fts`, `memory_vec` and their triggers are gone), and registers itself as its last statement (`INSERT INTO schema_version(version) VALUES (1);`, `001_baseline.sql:502`) — `run_migrations` executes a migration's SQL and nothing else. Migration 2 rebuilds `session` with the conversation's working state in place of the session summary's four columns — five columns, `working_state` (the JSON, `''` until written), `working_state_version` and `working_state_through` (`INTEGER NOT NULL DEFAULT 0`), `working_state_updated_at` and `episode_note_id`, and a sixth, `inherit` (`INTEGER NOT NULL DEFAULT 1`, CQ-5's "Start fresh") — copying every other column and re-creating the four indexes, and registers 2 (`002_working_state.sql:47`). Migration 3 deletes the `file_assets` rows whose bytes lie inside a project's own folder — `project_root` set and `storage_path` beginning with it and a separator, compared with `substr` — their versions and every attachment link going by cascade, and registers 3 (`003_no_project_store_rows.sql:17`; `migration_3_deletes_the_rows_whose_bytes_lie_inside_a_projects_own_folder`, `database/tests.rs:1299`). Migration 4 adds `file_assets.in_project INTEGER NOT NULL DEFAULT 0` — `1` marks a result file's pointer row (ST-12, R35) — and rebuilds `idx_file_assets_addr` as `(COALESCE(project_root, ''), in_project, rel_path)`, so a result file may share its path with a by-product's or an upload's address, and registers 4 (`004_project_files.sql:14`; `a_version_3_database_migrates_to_4_with_every_row_outside_the_project`, `database/tests.rs:1384`). The cases at open (`run_migrations`, `database/mod.rs:107`), all decided from `schema_version` (its `MAX(version)`) before any SQL runs: a fresh database (version 0: no table, or no row) runs every registered migration in one transaction and opens at the newest, 4 today; one below the newest runs the migrations it is missing — a version-1 database runs 2, 3 and 4 in place, its free-text summary not copied and `through` at 0, so the next writer reads what the summary covered (`a_version_1_database_migrates_to_the_working_state_in_place`, `database/tests.rs:1142`); one at the newest returns early; and one **above** the newest is refused with nothing changed (`:138`) — which is what every pre-squash database reads as, 42 from before the memory redesign and 43–45 after it. That is the only refusal, so its text names both builds that could have written the file: a newer one (use it), or one from before the re-baseline, whose database cannot be read or upgraded — run `openalpaca config reset --factory`, which deletes it and `llm.toml`'s keys (SQ-1a; the text of record is `tasks/store-revision/design.md` §1.4). `a_database_newer_than_this_build_is_refused_without_changing_its_schema_or_data` (`database/tests.rs:68`) pins that text whole, the verb exactly once and the file's schema and rows unchanged, and fixture 06 (`tests/fixtures/memory/06-newer-database-refused.json`) states the same; the refusal reads only `schema_version`, so it needs no SQLite module. **To add migration 005:** drop `005_<name>.sql` in `crates/openalpaca_storage/src/migrations/` — the loader reads the registry, not the directory, but the file's number is the version it registers (SQ-1) — end its SQL with `INSERT INTO schema_version(version) VALUES (5);`, append `Migration { version: 5, name: "<name>", sql: include_str!("005_<name>.sql") }` to `MIGRATIONS`, and bump the comment above it (`migrations/mod.rs:16-18`, "Future schema changes start at version 5") to 6. The assertions on a fresh or reset database's version already read the newest registered migration (`newest_version()` = `MIGRATIONS.last()`, `database/tests.rs:17`) or the registered list, and the refusal tests stamp `newest + 1` or 99 (asserted above the newest), so they move with it. `BASELINE_VERSION` stays 1 and goes on meaning "oldest openable schema". The file's first `--` comment becomes its summary in the generated `docs/api/database/` docs (`python3 scripts/gen_api_docs.py`, whose parity check wants one `NNN_*.sql` file per registered migration). Comments and docs across the tree still cite the old numbers ("migration 041", `039_sessions.sql`, "migration 044") as provenance for when a column or index arrived; those are true as history and the files are in git, but nothing resolves them in the tree any more (SQ-3). `lane_followups.unattended` and `task.unattended` (both `INTEGER NOT NULL DEFAULT 0`) preserve the "nobody here can answer a confirmation" declaration for parked work. `tool_execution_log` and `skill_execution_log` each have a `timestamp`-leading index; the two "today" counts behind `GET /v1/tools` / `GET /v1/skills` name them with `INDEXED BY` because the planner otherwise prefers the grouping index and scans.

**Memory is not in the database** (the memory redesign; design `tasks/memory-redesign/03-design.md` §2–§7c). A note is one Markdown file with canonical frontmatter (`id` UUID, `title`, `kind` ∈ `NoteKind`, `status` ∈ `NoteStatus` — `active | candidate | archived`; *superseded* is derived from links, never stored), written through one hardened atomic path (0700 dirs, 0600 files, no-follow opens, a per-component link check on the way to the partition). A **partition** is one owner's notes in one scope: `<home>/memory/owners/<owner-key>/` or `<home>/projects/<name>/memory/owners/<owner-key>/` (`<owner-key>` = first 32 hex of `sha256(owner_id)`; the project is what `store::projects::resolve` makes of the request's `request_workspace_root` — the nearest folder at or above it that is a recorded project's root or holds `.git` — and has a partition only once registered, R12; the partition is created lazily on the first write, keyed `proj-<owner-key>-<16 hex of sha256(project id)>` and bound by the `project_id` its control snapshot carries, so a re-point touches neither, R18–R20; MD-5's marker half and MD-7's `.gitignore` are superseded by the storage design's ST-1 and ST-6). Each partition's authority lives in **one control snapshot**, `state/memory-control/<partition-key>.json` (`memory_files/mod.rs:106`): the revision the service last wrote per note (SHA-256 of the file's bytes), each note's **origin** (`user` > `extracted_user` > `imported` > `external` > `extracted_other`), the tombstones of forgotten notes, and a single `pending` field for crash recovery; a missing or invalid snapshot **quarantines** the partition until `openalpaca memory doctor --repair`. Search is a separate, disposable SQLite file, `state/cache/memory-index-v1.sqlite` (`memory_index/mod.rs:58`, `:545` — the name is unchanged while its tables are `SCHEMA_VERSION` **6**, `:90`: L2 added `note_source` and `supersedes`, L10a the dates, LQ17 the layout revision of design 09 §6.5 at 4, its repair round's wider unsegmented scripts at 5, and the storage design's project-id partition keys at 6, R21): the chunks' normalized text held once, under three contentless FTS5 tables — `fts_word` (`unicode61` over title, aliases, tags and body, split where an unsegmented script meets a letter or digit of another, queried for whole words and, when a term's last token has ≥ 3 characters and is not a stop word — or is a number following another token, at any length (`10:30` in `10:30am`, `3.12` in `3.12rc1`) — and the term carries no unsegmented character, word beginnings (`query::is_prefix_term`): `prefer` finds `prefers`, reported `prefix`; when that query fills its cap, each such term is searched again as a whole word, in the header ranked and alone in bodies unranked), `fts_tri_head` (trigram over title, aliases and tags) and `fts_tri` (trigram over the bodies of chunks carrying a character of a script `unicode61` cannot split into words — CJK, Thai and the other scripts written without spaces, Devanagari, Tamil and the other scripts built with vowel signs, `query::is_unsegmented` — searched only by a term carrying one) — every term ORed, so nothing finds a term *inside* a word of an English body (`presso` in `espresso`), a bounded substring pass for 1–2 characters, filters (status, derived supersession, tombstones, same-`fact_key` losers, validity — and, for automatic recall, conversation summaries) before the limit, **no embedding and no model**. `MemoryService` (`crates/openalpaca_core/src/memory/service/`) is the one implementation behind the main loop's and the skill tier's per-turn recall — **index-first by default** (`[orchestrator.memory] recall_mode = "index"`: pinned notes, the top 2 as excerpts, then up to 8 one-line index entries the model opens with `memory_read`; `excerpts` delivers up to 8 notes as excerpts; a skill that cannot call `memory_read` gets `excerpts`), within 8 KiB and 2 KiB pinned, every hit re-read and re-hashed, delivered as quoted data outside the cached prompt layer (`service/recall.rs:23`, `service/types.rs:737`) — the lead's opening recall, the eight tools, the learners (`memory/learning/` for conversations and episode notes, `memory/task_extraction/` for runs — which read a model's answer tolerantly, `<think>` tags, prose around the JSON or a bare items array, through `task_extraction::read_json_answer` (`task_extraction/mod.rs:584`), LQ13, and offer the extractor no key held only by the chat model's own notes, `memory_index::LEARNING_KEY_HOLDER`, LQ14) and the `/v1/memories*` routes; one writer slot per partition; freshness is the service's own writes plus a 30 s stat-scan reconciliation (`apps/openalpacad/src/background.rs:295`, interval `:368`) and per-read verification — no watcher; the scan lists `notes/` with one `getattrlistbulk(2)` pass on macOS and `readdir` + `lstat` elsewhere, the same entries and fields bit for bit (`memory_files/dirstat.rs`, LQ16: 221–233 → 99–108 ms over 100,000 files). The index is kept note by note: a partition's first pass in a process reads its fingerprints back from the rows (scale slice S1), so only a missing, unreadable or schema-bumped cache — or one grown past twice its size after its last rebuild, which the idle tick rebuilds once it has merged the FTS segments and truncated the WAL (S5) — is rebuilt whole, on a blocking worker after the daemon already serves (`MemoryService::open_default_deferred`, `background::spawn_memory_index_rebuild`, `:258`); meanwhile recall and search answer from a bounded scan of the note files — the index's filters and ranking in memory over at most the newest `FILE_SCAN_MAX_NOTES` = 10,000 notes (`MemoryIndex::scan_search`, `memory_index/scan.rs:42`; `index_state: rebuilding`), background learning's lookups wait the rebuild out and read again if one starts under them (`read_index`), while a read a person or a model waits on never waits — it answers from the files or, with no file-scan answer, is refused `index_rebuilding` (`memory_timeline`; `read_index_or`, `service/mod.rs:547`), and open runs no `quick_check`, so a corruption error met by any index read owes the rebuild (`indexed`, S6). A forgotten note's file put back mid-process is left out and deleted by every scan (S3). A reply waits at most 1.5 s for its recall and its suggestions (`REPLY_MEMORY_DEADLINE`, `prompt_ctx/sources/memory.rs:47`, S7). Reads go through a **parse cache** and a **snapshot cache** (`memory_files/cache.rs`: up to 128 MiB of parsed notes keyed by each file's stat identity; a file whose stat was taken within 100 ms of its last change — 3 s on whole-second file systems — is re-hashed at every read until it settles, 09 rev 3.9). An index failure after a write landed is logged and left to the next reconciliation, never returned (residue R6). **Episode notes** — conversation summaries: `episode`, origin `extracted_other`, active, written at the conversation's close by its own summariser call over its rows (design 11 §3.4, owner decision CQ-11) — are found by search, the timeline and the Memory view, never delivered by automatic recall (a pinned one is), and forgotten with their conversation. Nothing ages or prunes a note, nothing replaces one by similarity, and a factory reset leaves the notes — each project's folder under `projects/` with its `project.json` included — the snapshots and the index in place (the new owner id orphans them until `openalpaca memory adopt`, which finds a project's partitions by the project id).

Data directory: `~/.openalpaca/` (all platforms — `store::home_root()`, overridable with `OPENALPACA_HOME_STORE`; absolute paths only). `state/` holds `openalpaca.db` (+ `-wal`/`-shm`), `discovery.json`, `openalpacad.lock`, `.master_key`, `repl_history` (the CLI chat's line history), `backups/`, `logs/` (`daemon.log`, `gui.log`), `memory-control/` (one control snapshot per memory partition, `<partition-key>.json` — never swept, the notes' authority and forget history), `cache/memory-index-v1.sqlite` (the memory search index, `store::cache_dir()` — regenerable, rebuilt from the notes when missing; an old `cache/fastembed/` from before the memory redesign is owned by nothing and deleted only by hand); `assets/` exists only on a machine whose uploads predate D2 — nothing reads, writes or moves it, the pre-D2 tolerance having been removed on 2026-09-28 (SQ-2 (c)), and the factory reset a pre-squash store takes deletes every row that pointed there; `config/` holds the runtime config the GUI- and CLI-managed daemons are started with; `plugins/` (dropped plugin dirs + `.permissions.toml`, `.config/<name>.toml`, `.data/<name>/`), `artifacts/`, `uploads/`, `sessions/` and `memory/` (`memory/owners/<owner-key>/` — `notes/<uuid>--<slug>.md`, `.history/<uuid>/<revision>.md` for the last five service-written revisions, and a rebuildable `MEMORY.md`) sit at the root, with `scratch/` holding one working folder per conversation with no project (`scratch/<conversation id>/`, made at first use, removed with the conversation), and `artifacts/kept/` and `uploads/kept/` holding a deleted project's files that a surviving conversation still shows. `projects/<name>/` is one project's folder (the name as in the paragraph on Stage 1 above) and holds `project.json` (`{version, id, root, created_at}`, 0600) and content only — `artifacts/` (with `.versions/`), `uploads/`, `memory/` (the project's partitions; their control snapshots live in `state/memory-control/`); session logs always live in `sessions/`. A project is registered — its folder created — only where the daemon accepts work for it, and resolved purely everywhere else (`store::projects::resolve`). Nothing of OpenAlpaca's own is ever written inside a project's own folder — since the storage design's Stage 2 an agent writes and edits the project's files there, each write asking first, a written file listed by a pointer row (`file_assets.in_project`) — and an `.openalpaca/` an earlier build left there is never read (ST-9). The home root is self-describing: `ensure_store()` seeds a `README.md` with a retention class per entry plus `.layout` (version, and `install_id` on the home root), each written only when absent — since SQ-2 (b) and (d) (2026-09-28) nothing refreshes an old README or adds a key to an existing `.layout`, whose unreadable line 1 is still repaired. A development build's data at `~/Library/Application Support/OpenAlpaca` (macOS) / `~/.local/share/openalpaca` (Linux) is **not** moved here, and since SQ-2 (a) nothing looks at it (see the D1 bullet above).

## Gotchas

- `.gitignore`'s `# Markdown Documentation (Except Manuals)` block blanket-ignores `*.md`. A new doc is invisible to git until whitelisted with a `!path` line — in that block, or in the `# UI rework reference docs` block near the end of the file; confirm with `git check-ignore -q <file>` (exit 0 = still ignored) before calling it committed. Cite the blocks by those comment headers, never by line number: the numbers have moved twice.
- `SystemEvent` and `ServerEvent` are matched exhaustively with no catch-all: a new variant needs an arm in `apps/openalpacad/src/event_bridge.rs:30` (system) or `apps/openalpacad/src/events/persistence.rs:12` (server) in the same commit. The newest pair is `memory_changed`: `SystemEvent::MemoryChanged` (`crates/openalpaca_core/src/events.rs:610`, published from inside `MemoryService` for every write and every external change a reconciliation finds) → the bridge arm (`event_bridge.rs:247`) → `ServerEvent::MemoryChanged` (`crates/openalpaca_api/src/events/mod.rs:487`), whose persistence arm returns `Ok(0)` (`persistence.rs:25`) like `daemon_shutting_down`'s — never an `event_log` row. Nothing in the GUI fails to compile on a new variant, so give it its GUI homes in the same wave: `invalidationKeysFor` (`apps/openalpaca-gui/src/lib/query-client.ts` — `memory_changed` → `["memory"]`, `:181`), the `DaemonEvent` union (`lib/events.ts`), and, for a *persisted* event, `lib/api/run-events.ts` (F3). Learning v2 added **no** variant, but `ToolConfirmationRequested` (both enums and the SSE frame) gained `preview` (a daemon-written text, a note's title and body for `memory_confirm`) and `per_call`: **live only** — its persistence arm (`persistence.rs:301`) writes ids alone, so a later-forgotten note's title never reaches `event_log`; keep it that way.
- **An OpenAI(-compatible) tool definition carries `"strict": true` only when `openai_tools::strict_mode_compatible` accepts its schema** (residue R8, `crates/openalpaca_llm/src/providers/openai_tools.rs:106`; Ollama shares the builder). The check is an allowlist: closed objects with every key in `required`, only documented keywords each in its place, a `$ref` standing alone, 10 levels of objects at most; anything else goes out without the flag, silently — today `memory_confirm` and `file_list` keep it, although 22 builtins set `strict: Some(true)`. A new strict tool must pass the check or it quietly loses strict mode; `every_builtin_goes_to_openai_with_strict_only_where_strict_mode_accepts_it` (`crates/openalpaca_core/src/tools/builtins/tests.rs:1727`) pins every builtin against an independent restatement of OpenAI's rules, and a new per-request definition function has to be added to its list.
- **A streamed frame yields every event it carries** (V1). The OpenAI-compatible parser (`crates/openalpaca_llm/src/providers/openai/streaming.rs`, shared by every OpenAI-compatible base — Ollama included) decodes a frame into a `Vec<StreamEvent>` and drains that queue before reading the next line; one `return` per matching field was the bug class, not one bad arm. Ollama puts a whole tool call — `id`, `name` **and** `arguments` — in a single frame, and returning at `id` dropped the arguments, which made every main-loop tool call arrive empty. Any new test for an OpenAI-compatible stream must include that shape (single-frame tool call; two tool calls in one frame; content + tool calls in one frame; tool calls + `finish_reason` in one frame), not just the split-frame shape OpenAI itself sends.
- Oversized tool results: a loop **with** a session log spills the whole result to `sessions/<id>/results/` and hands the model a stub — the first 2 KB plus `result_ref=file:results/…` — which the scoped `read_result` builtin pages back in; a loop **without** one — any caller that leaves `LoopConfig.session_log` at `None`, which is every non-session caller — falls back to an inline cut at the same threshold — one number, `[orchestrator.sessions] tool_result_inline_bytes`, default 32 KB (`MAX_TOOL_RESULT_SIZE`, `crates/openalpaca_core/src/runner/agentic_loop/tool_helpers.rs:4`). An `Err` result stays inline but cuts head+tail, so a compiler or test failure keeps the assertion at the end (`utils::text::head_tail`, `crates/openalpaca_core/src/utils/text.rs:77`). `read_result` is offered wherever a spill can happen (R84): on the main loop's per-request surface when this daemon has a session log **and** a database (`tools/builtins/main_loop.rs`), on the lead's hand-assembled surface when the lead's own template grants it (`runner/lead_agent/mod.rs`, the `artifact_write` shape), and all nine shipped `config/agents/*.md` templates grant the capability. It is still a **grant, not ambient** — the constructor-appended set is untouched (owner decision T15, taken on 2026-10-17 as recommended — the fixed ambient set `{workspace_read, workspace_write, read_result}`, beaten by `denied_capabilities` — is not built), so an agent whose template does not name `read_result` is refused it and reads a stub it cannot follow.
- `config/llm.toml` is seeded on first daemon start and is absent from a fresh checkout: without provider keys nothing can call a model, so the live steer eval and plan pre-check (d) need them — **except** a local Ollama, which needs no key at all (`[providers.ollama] enabled = true` and a pulled model is the whole setup; see `docs/Installation_Manual.md` → Local Models).
- Any test that enables Ollama must point at a mock or an unbindable port — `crate::test_util::MockOllama` (daemon, `#[cfg(test)]`) or `test_support::MockHttpServer` (`openalpaca_llm`, crate-private). Discovery is no longer gated on a key, so a fixture still naming `http://localhost:11434/v1` reaches whatever the developer's machine has installed and the assertions become machine-dependent (`hot_reload/llm_dedup_tests.rs` and `provider_enabled_tests.rs` use `http://127.0.0.1:1/v1` for exactly this).
- **`event_log` grows forever; nothing prunes it** (W6, verified — do not read this as a request to build a sweeper). Two writers: `EventBroadcaster::persist` (`apps/openalpacad/src/events/persistence.rs`) writes a row for **every** `ServerEvent` but `heartbeat`, `daemon_shutting_down` and `memory_changed` — 33 of the 36 variants, `task_status`/`workflow_*`/`tool_*`/`extension_*` among them — and the security sandbox writes `security_violation`, `tool_auto_approved` and `tool_approval_unavailable` (`crates/openalpaca_core/src/security/sandbox/mod.rs:247`, `:509`). The sandbox half is new in practice: before V2 wired a database into the production sandboxes, `SandboxManager::with_db` had no production caller and those rows existed only in tests. The one periodic sweep, `background::spawn_telemetry_cleanup`, is `SkillExecutionRepository::cleanup_old(90, 7)` — `skill_execution_log` and `tool_execution_log` only, never `event_log`. `event_log` rows go away in exactly two places, both deliberate and neither periodic: a factory reset (`openalpaca config reset --factory` deletes the database file outright — `Database::factory_reset` and its 29 `DELETE`s are gone) and a project purge (`POST /v1/workspaces/purge` → `artifacts/mod.rs:1892`, which deletes the rows of that workspace's runs by `task_id`). Readers are `GET /v1/events/history` and `dispatcher/outcome.rs:156`. Whether the table needs a retention pass is nobody's default to adopt.
- **Memory search is lexical, and that is the design, not a gap to fill** (MD-1). There is no embedding, no vector table, no reranker and no model on any memory path — only FTS5 `unicode61` plus two trigram tables (`crates/openalpaca_storage/src/memory_index/query.rs`), with aliases as the remedy for paraphrase and cross-language recall. Do not add an embedder, a `sqlite-vec` table or a "semantic" fallback: plan slice 4 says a recall miss is answered with aliases, ranking or the bounded follow-up search, never by quietly restoring a model, and the tool descriptions say "no meaning-based search" on purpose (`tools/builtins/memory_tools.rs:248`). A recall test must share with the note it expects a word, a word's beginning (`prefer` finds `prefers`), an alias, or a ≥ 3-character substring of its title, an alias, a tag or unsegmented text (CJK, Thai, Devanagari, Tamil and the rest `query::is_unsegmented` names) — since LQ17 (index schema 4; 5 widened the scripts) a substring inside a word of an English body finds nothing. The index file is disposable: a change to its tables **or to what a row holds for the same note bytes** — the chunker, `query::normalize`, `authority_rank`, the service's `record_for`, how `date` or `norm_title` is derived, the tokenizers, `query::split_scripts` and the ranges of `query::is_unsegmented` — bumps `memory_index::SCHEMA_VERSION` (`memory_index/mod.rs:90`, 6 today), and never needs a migration. Since scale slice S1 rows survive restarts and are re-derived only when their note changes, so without the bump the old rows are served for good; with it an old cache is deleted and rebuilt from the notes in the background. The notes and `state/memory-control/` are the only authority; never write a memory file, a snapshot or a `.history/` copy except through `memory_files`/`MemoryService`.
- **The memory index layout is design 09 §6.5 (LQ17), and a change to it must pass that section's retrieval proxy.** Schema 6 (`memory_index/mod.rs:90`; the layout of 5 — 6 changed only the project partitions' keys, R21) holds each chunk's normalized text once under three contentless FTS5 tables (`:486`, `:491`, `:496`: `fts_word`, `fts_tri_head`, `fts_tri`) and reports a word beginning as `MatchReason::Prefix` (`memory_index/search.rs:34`; the rule is `query::is_prefix_term`, `query.rs:384`). Before shipping a change to the tables, the tokenizers, `query::is_unsegmented`, the prefix rule, term routing or ranking, run the proxy on the parent commit and on the change and compare row for row: the evaluation harness's dry run (`scripts/eval/memory/README.md` → *A dry run with no model*: system D with no model and no judge, outbound networking denied, in both recall modes, over the 470 held-out and 150 tuning questions — `rows_with_every_relied_note_delivered`, `…_listed_or_delivered` and each row's `relied_notes_delivered`/`listed`). No net loss of relied-note delivery is the bar, and a lost row goes to the lead with its reason (tq-0032, accepted 2026-09-27, is the one on record). The reference reports are in a session scratchpad and are not tracked, so regenerate the baseline; the index's own contract tests are the query fixtures `crates/openalpaca_storage/tests/fixtures/memory/21-…` to `24-…` and `26-…` (`memory_index/fixture_tests.rs`), and the benches are `memory_index::bench` and `memory::service::bench`, release, on a quiet machine.
- **A chat model's replacement or edit of a note the user saved becomes a suggestion (LQ11) — never a refusal and never a parallel note.** On the `ModelTool` surface a `memory_store` whose `supersedes` names a note of origin `user`, `external` or `imported`, a store whose `fact_key`'s R9 winner is such a note, and a `memory_update edit` of one that changes its title, body, aliases, tags, key or validity are written as a candidate of origin `extracted_user` naming that note (`ReplacePolicy::SuggestUnlessLearned`; `MemoryService::store`, `memory/service/mod.rs:1935`, `suggest_edit`, `service/mutations.rs:197`); the note is untouched until the person confirms, the tool result says it is a suggestion and not to store it again, and the Memory view labels it "Suggested by Alpaca". Before LQ11 a refused supersede left the model storing a second, contradicting active note instead (L-S: 4 of 8 suggestions missing — in all four the model had stored the new value itself; the refusal is proven for one). Still refused `authority_conflict`: archive of a `user` note, an edit of one that changes nothing a suggestion carries (only `review_after`), an edit of a saved note a forget took out of recall, and — from any surface but the user's, since LQ10 (2026-09-28) — an edit that sets or changes a conversation summary's `fact_key` (`memory_files/partition.rs:2008`, in `Partition::update`). A pending candidate's forget suppresses no row the note it names, or any saved note, cites (`memory_files/partition.rs:2191`, in `forget_each`). A new model-facing write path goes through `store`/`suggest_edit`, never around them; the tests are `memory/service/tool_suggestion_tests.rs`.
- **A note the chat model's `memory_store` wrote is recognised by origin `extracted_user` with no `observed_at` (LQ14's datum) — not by `sources: []`**, since a tool call may cite rows. It holds because only the `Extraction` surface may set `observed_at`, and every note the extractor writes from the user's words carries one. - **No test reads or writes the developer's `~/.openalpaca`, and every test that resolves, registers or lists projects holds its crate's home-store guard** (storage design Stage 1). That is a test that reaches `store::projects::register` — a chat turn, an upload, a memory write or a dispatch with a project, or one that registers a project itself — and one that only resolves a project path or lists projects, which reads `<home store>/projects/` (the lead's R-S2: no test reads `~/.openalpaca`, not even its metadata).
