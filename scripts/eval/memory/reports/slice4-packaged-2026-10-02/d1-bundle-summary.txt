## Two different daemon builds ship in one archive (an observation; nothing was changed)

`libexec/openalpacad` and the `.app`'s `openalpacad` are **not the same binary**. They differ by 2,688 bytes and in sha256. `package-macos.sh` installs `target/release/openalpacad` from `cargo build -p openalpaca -p openalpacad`. The sidecar comes from `prepare-sidecar`'s own `cargo build -p openalpacad`, and cargo's feature unification resolves the shared crates differently for the two invocations: the `-p openalpacad`-only build recompiled `openalpaca_llm`, `openalpaca_core`, `openalpaca_connectors` and `openalpaca_plugins` (`build/03-tauri-build.log` lines 4–10). Both builds come from the same commit. D2 ran the `.app`'s binary (`bdaa22a2…`), as the task says. The CLI-managed daemon that `install.sh` would set up is the other build. This was already the case before this branch and is reported, not fixed.
